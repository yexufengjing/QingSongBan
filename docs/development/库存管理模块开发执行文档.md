# 库存管理模块开发执行文档

## 1. 文档说明

本文档用于指导现有手机端工作管理 App 中“库存管理模块”的设计与开发。

本模块面向个人日常管理的小仓库物资场景，设计目标不是构建企业级 ERP，而是以**简单、稳定、可手动调整、避免数据错乱**为第一原则。核心业务包括：

- 从总库或其他来源领取物资并办理入库；
- 员工从小仓库领取物资并办理出库；
- 实时查询当前库存；
- 定期盘点并处理盘盈、盘亏；
- 设置最低库存并进行预警；
- 建立待采购/待领取清单；
- 查询完整库存流水；
- 维护物资基础信息；
- 与现有人员管理、物品领取/劳保福利、Excel 导出、备份恢复等功能联动。

本项目继续沿用既有技术基线：

- Flutter + Dart
- Riverpod
- GoRouter
- Drift + SQLite
- 本地优先、离线可用
- Repository 分层
- 暂不接入服务器、云数据库、登录和多人协同
- 支持后续接入 Excel 导入导出、本地提醒及备份恢复能力

# 2. 模块功能概述

库存管理模块形成以下完整业务闭环：

**物资档案 → 入库 → 出库/员工领取 → 当前库存 → 库存流水 → 库存盘点 → 库存预警 → 待采购/补充 → 再次入库**

其中：

1. **物资档案**  
   管理物资名称、型号、单位、分类、最低库存、存放位置等基础信息。

2. **入库管理**  
   记录从总库领取、采购、退回、调拨、盘盈等入库行为。

3. **出库管理**  
   记录员工领取、其他领用、调拨、盘亏等出库行为。

4. **员工领取记录**  
   保持简洁表格布局：  
   **日期｜物品名称｜型号｜领取数量｜领取人｜备注**

5. **当前库存**  
   实时展示每种物资当前数量及库存状态。

6. **库存流水**  
   记录所有库存变化，并可反查变化前数量、变化数量、变化后数量及来源业务。

7. **库存盘点**  
   对账面库存与实际库存进行比对，自动生成盘盈/盘亏调整记录。

8. **最低库存预警**  
   当当前库存小于或等于最低库存时进行提醒。

9. **待采购/待补充清单**  
   可由用户手工建立，也可由库存预警一键加入。

10. **人员联动**  
    员工领取物资时优先从现有人员档案选择领取人，并自动带出所属单位。

11. **数据导出**  
    后续支持导出当前库存表、员工领取表、入库记录、出库记录、库存流水、盘点表及待采购清单。

# 3. 需求说明

## 3.1 核心业务原则

### 3.1.1 当前库存支持手动修改

本 App 为个人自用工具，库存管理优先保证简单、稳定和可调整，因此允许用户直接手动修改当前库存。

手动修改库存时建议采用轻量处理：

- 用户可以在物资详情页或库存调整入口直接修改当前库存；
- 修改前显示原库存，修改后显示新库存；
- 可选填写调整原因或备注；
- 系统自动记录一条“手动调整”记录，便于以后查看；
- 不要求建立复杂的审批、冲销或企业级库存凭证逻辑。

例如：

> 原库存：18副  
> 手动调整为：20副  
> 原因：实际盘点后修正

核心目标是保证修改完成后：

- 当前库存数值立即更新；
- 列表、详情、预警状态同步刷新；
- 不出现页面显示不一致或缓存旧数据的问题。

---

### 3.1.2 库存变化保留简单记录

为方便日常追溯，入库、出库、盘点和手动调整后建议自动生成库存变化记录。

记录至少包含：

- 物资；
- 时间；
- 变化类型；
- 修改前库存；
- 变化数量；
- 修改后库存；
- 备注。

本项目不追求企业级账务流水设计，不要求复杂的不可撤销、冲销或审计机制。

用户可根据实际需要删除明显误录的普通记录，但删除已经影响库存的数据时，必须同步重新计算或修正当前库存，避免库存与记录不一致。

---

### 3.1.3 历史记录不能因基础资料变化而失真

例如：

- 员工后续离职；
- 员工所属单位变化；
- 物资名称后续修改；
- 物资型号后续调整。

历史出库记录仍应保持当时业务信息。

因此业务记录中建议保留必要的快照字段，例如：

- employeeNameSnapshot
- departmentNameSnapshot
- materialNameSnapshot
- modelSnapshot
- unitSnapshot

同时继续保留关联 ID，便于查询当前档案。

# 6. 入库管理

## 6.1 入库业务类型

首版至少支持：

- 总库领取
- 采购入库
- 退回入库
- 调拨入库
- 盘盈入库
- 其他入库

## 6.2 入库字段

- 入库日期
- 入库类型
- 来源
- 经办人
- 备注
- 入库明细

每条入库明细包括：

- 物资
- 型号规格
- 数量
- 单位
- 参考单价，可选
- 备注

## 6.3 业务规则

保存入库单时：

1. 校验明细；
2. 创建入库记录；
3. 增加物资库存；
4. 为每条明细创建库存流水；
5. 刷新库存首页统计；
6. 若入库后库存已高于最低库存，自动取消对应低库存状态。

## 6.4 展示文本

系统可以自动生成自然语言摘要，例如：

> 2026年9月29日，于特钢总库领取加厚劳保手套50副。

该文本仅用于展示，不作为核心业务数据。

# 7. 出库与员工领取管理

## 7.2 出库类型

首版建议支持：

- 员工领取
- 部门/公用领取
- 调拨出库
- 盘亏出库
- 其他出库

## 7.3 员工领取字段

- 日期
- 物资
- 型号规格
- 数量
- 单位
- 领取人
- 所属单位
- 用途
- 经办人
- 备注

## 7.4 人员联动

领取人优先从现有人员管理模块选择。

选中人员后自动带出：

- 姓名；
- 所属单位；
- 人员类型；
- 当前状态。

同时保留“手工填写领取人”能力，以兼容：

- 外部人员；
- 临时人员；
- 无人员档案的特殊领取。

## 7.5 出库校验

提交前必须校验：

- 数量 > 0；
- 物资存在；
- 当前库存充足；
- 领取人或领取对象不能为空；
- 日期合法。

当领取数量 > 当前库存时：

**禁止提交。**

提示例如：

> 当前库存仅剩 3 副，本次领取 5 副，无法完成出库。

## 8.1 库存列表字段

建议展示：

- 物资名称
- 型号
- 单位

- 最低库存

- 正常

# 10. 库存盘点

## 10.1 盘点流程

1. 新建盘点；
2. 系统读取当前账面库存；
3. 用户填写实盘数量；
4. 自动计算差异；
5. 显示盘盈/盘亏；
6. 用户确认盘点；
7. 自动生成库存调整业务；
8. 自动生成库存流水；
9. 保存盘点历史。

## 10.2 盘点明细

每条盘点明细包括：

- 物资
- 型号
- 单位
- 账面数量
- 实盘数量
- 差异数量
- 差异类型
- 备注

## 10.3 差异规则

差异数量：

`实际库存 - 账面库存`

- > 0：盘盈
- < 0：盘亏
- = 0：一致

确认后：

- 盘盈 → 自动创建盘盈入库
- 盘亏 → 自动创建盘亏出库

## 11.1 触发条件

`warningEnabled = true`

`currentStock = 0`

- 查看物资详情；
- 快速入库；
- 加入待采购；
- 修改最低库存。

# 13. 库存流水

## 13.1 流水字段

每条库存流水建议保存：

- id
- materialId
- materialNameSnapshot
- modelSnapshot
- unitSnapshot
- occurredAt
- transactionType
- sourceType
- sourceId
- stockBefore
- quantityChange
- stockAfter
- operatorId
- operatorNameSnapshot
- remark
- createdAt

## 13.2 quantityChange 规则

入库：

`quantityChange > 0`

出库：

`quantityChange < 0`

例如：

原库存 20 副，员工领取 2 副：

- stockBefore = 20
- quantityChange = -2
- stockAfter = 18

## 13.3 流水不可直接修改

流水应由业务层自动产生。

UI 不提供：

- 新建库存流水；
- 手动修改库存流水；
- 普通删除库存流水。

# 16. 分层职责

## 16.1 UI / Presentation

负责：

- 页面展示；
- 表单输入；
- 状态展示；
- 用户交互；
- Provider 订阅。

不负责：

- 直接计算库存；
- 直接写数据库；
- 手动拼接复杂业务。

## 16.2 Riverpod Provider

负责：

- 页面状态；
- 加载状态；
- 筛选条件；
- 调用 Repository / Service；
- 刷新列表。

Provider 不直接堆积大量数据库 SQL 或复杂库存事务。

## 16.3 Repository

负责：

- DAO 封装；
- 数据读取；
- 业务数据保存；
- 组合查询；
- 事务入口。

## 16.4 Domain Service

建议增加：

```text
InventoryService
InventoryTransactionService
StocktakeService
InventoryWarningService
```

其中 `InventoryTransactionService` 负责所有实际库存变化。

禁止不同页面各自实现一套库存增减逻辑。

# 28. InventoryTransactionService

核心库存变化统一由 Service 完成：

```dart
abstract class InventoryTransactionService {
  Future<void> createReceipt(...);
  Future<void> createIssue(...);
  Future<void> confirmStocktake(...);
  Future<void> adjustStock(...);
}
```

每个方法内部必须使用数据库事务。

例如员工领取出库：

```text
BEGIN TRANSACTION

1. 查询当前库存
2. 校验库存是否充足
3. 创建出库记录
4. 更新 material.current_stock
5. 创建库存变化记录
6. 刷新库存预警和页面状态

COMMIT
```

任何一步失败：

```text
ROLLBACK
```

这样避免出现：

“出库单保存成功，但库存没有扣除”

或：

“库存扣除了，但流水没有生成”

# 44. 删除与修改规则

本项目为个人自用工具，不设计复杂的企业级撤销、冲销和审批机制。

建议规则：

- 物资基础资料支持正常编辑；
- 普通误录记录允许删除或修改；
- 如果修改或删除的记录会影响库存，系统必须同步重新计算当前库存；
- 对于已经长期使用的历史记录，优先保留原记录并通过“手动调整库存”修正，减少复杂逻辑；
- 所有操作完成后统一刷新库存列表、详情页和预警状态。

重点不是限制用户修改，而是保证修改后数据一致。

- 用户连续点击“保存”；

- 页面返回后重复提交。

建议：

提交期间禁用按钮，并由 Service 层进行最终状态校验。

# 49. 开发中的重点约束

本模块坚持“简单、稳定、可手动调整”的原则：

1. 当前库存允许手动修改；
2. 入库、出库、盘点和手动调整后必须同步刷新当前库存；
3. 关键写入操作使用数据库事务，避免保存一半导致数据错乱；
4. 不设计复杂审批、冲销、审计锁定机制；
5. 删除或修改影响库存的记录时，必须同步修正库存；
6. 库存计算逻辑集中在 Service 或 Repository 中，不分散到多个页面；
7. Provider 主要负责页面状态，不直接堆积复杂数据库逻辑；
8. 所有页面读取统一数据源，避免列表与详情显示不一致；
9. 人员领取优先关联现有员工档案，同时允许手工填写；
10. 福利领取规则与库存数量管理保持分离；
11. 数据库升级必须提供 migration；
12. 所有数据离线可用；
13. 第一阶段不引入服务器和额外云服务；
14. 优先保证日常操作方便和数据稳定，不为了“企业级规范”增加无必要复杂度。

# 51. 总结

本模块第一优先级不是企业级库存账务，而是保证日常使用简单、稳定、可调整，同时避免数据错乱和状态不一致。

开发顺序必须围绕以下核心链路进行：

**物资档案 → 入库 → 出库 → 库存 → 流水**

然后在此基础上增加：

**盘点 → 预警 → 待采购 → 人员/福利联动 → 导出与统计**

只要库存更新逻辑集中、页面状态同步、数据库事务可靠，并保留基础变化记录，后续扩展月度统计、消耗分析、物资领取规则、采购记录和提醒功能时，都不需要推翻现有数据结构。
