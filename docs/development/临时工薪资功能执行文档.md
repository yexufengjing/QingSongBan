# 临时工薪资功能执行文档

> 适用项目：轻松办 App  
> 模块定位：人员与考勤模块完成后的增量功能  
> 执行对象：Luna  
> 技术基线：Flutter / Dart + Riverpod + GoRouter + Drift / SQLite，本地离线优先  
> 本文档用于指导“临时工工资造资、核算、确认、导出”功能的实际开发，不替代现有人员与考勤业务规则。

---

## 1. 开发目标

在现有“人员管理 + 考勤组 + 月度考勤名单 + 上午/下午半天制考勤 + 月度汇总 + 保险信息”基础上，新增“临时工薪资”模块。

核心业务规则：

```text
当月工资 = 当月实际出勤天数 × 日薪 + 补助 - 保险费用扣除
```

其中：

- 实际出勤天数直接引用对应造资月份的考勤汇总；
- 每个上午/下午出勤单元计 0.5 天；
- 日薪按照人员工种默认带出，但允许在工资批次中人工调整；
- 不同工种可以配置不同日薪；
- 工种及日薪允许用户自行新增、修改；
- 补助按人、按月填写；
- 保险费用扣除按人、按月填写或从已有保险信息带入默认值；
- 每月造资人员不使用固定名单；
- 默认根据“造资月份中实际存在出勤的人员”生成工资名单；
- 工资名单支持手动增加、移除及拖拽调整排列顺序；
- 工资批次确认后保存历史快照，后续日薪或人员资料修改不得自动改变已确认历史工资。

本模块第一版暂不计算：

- 加班工资；
- 奖金倍率；
- 个税；
- 法定节假日倍薪；
- 计件工资；
- 银行自动代发；
- 在线审批。

# 2. 模块入口规划

## 2.1 主入口

建议将“临时工薪资”放入现有底部导航的：

**汇总 → 临时工薪资**

理由：

- 工资属于月度汇总后的结算行为；
- 工资计算依赖月度考勤结果；
- 不应把工资入口混入“每日考勤”；
- 可以避免新增第六个底部导航项，保持现有首页 / 人员 / 考勤 / 汇总 / 我的结构稳定。

“汇总”页面建议增加功能卡：

```text
月度考勤汇总
人员变动
保险变更
临时工薪资
```

其中“临时工薪资”显示：

- 当前造资月份；
- 本月造资人数；
- 本月工资总额；
- 当前状态；
- 是否存在异常。

# 4. 工种与日薪配置

## 4.1 工种

第一版预置示例：

- 绿化工；
- 环卫工；
- 保洁员；
- 维修工；
- 司机；
- 其他。

所有工种允许：

- 新增；
- 修改名称；
- 启用 / 停用；
- 调整默认日薪；
- 设置备注。

不建议直接删除已被历史工资使用的工种。

如果工种已经存在历史数据，只允许“停用”。

## 4.2 日薪

每个工种对应默认日薪。

例如：

| 工种 | 默认日薪 |
|---|---:|
| 绿化工 | 120.00 |
| 环卫工 | 130.00 |
| 保洁员 | 110.00 |
| 维修工 | 160.00 |

以上仅为开发测试数据，真实金额由用户自行维护。

金额按“元”使用 SQLite `REAL` 保存，业务层统一保留两位小数。出勤仍以整数半天保存，展示和导出时换算为天数。

例如：

```text
120.50 元
数据库保存：
120.50 REAL
```

金额统一在业务层四舍五入到两位小数，避免浮点误差向页面和导出扩散。

## 4.3 日薪历史

建议日薪修改支持“生效月份”。

例如：

```text
绿化工

2026-01 起：120 元/天
2026-10 起：130 元/天
```

生成 2026 年 9 月工资时取 120 元。

生成 2026 年 10 月工资时取 130 元。

已经生成并确认的历史工资不重新计算。

推荐规则：

不建议为了这种情况建立新的工种。

# 6. 工资月份与工资批次

工资不直接散落保存，应使用“工资批次”。

例如：

```text
2026年09月临时工工资
```

一个月份原则上只有一个正式工资批次。

批次字段：

- 工资月份；
- 批次名称；
- 创建时间；
- 创建人 / 操作人；
- 工资人数；
- 出勤天数合计；
- 基础工资合计；
- 补助合计；
- 保险扣除合计；
- 最终工资合计；
- 当前状态；
- 确认时间；
- 锁定时间；
- 备注。

状态：

```text
未生成
  ↓
草稿
  ↓
待检查
  ↓
已确认
  ↓
已锁定
```

# 7. 造资人员名单生成规则

这是本模块最重要的规则之一。

## 7.1 不使用固定工资名单

工资人员不能简单复制“全部在岗人员”。

必须以：

**所选造资月份实际发生出勤的临时工**

作为默认工资名单。

例如：

张三：

- 7 月有出勤 → 进入 7 月工资；
- 8 月无任何出勤 → 默认不进入 8 月工资；
- 9 月重新出勤 → 自动进入 9 月工资。

这与现有“人员状态”和“月度考勤名单”分离规则保持一致。

## 7.2 默认候选条件

生成工资名单时默认满足：

```text
用工类型 = 临时工
且
参与工资核算 = 是
且
造资月份实际出勤天数 > 0
```

实际出勤天数直接读取该月考勤汇总。

## 7.3 特殊人员人工处理

工资批次允许：

- 手动增加人员；
- 手动移除人员；
- 恢复被移除人员。

手动增加时应显示提示：

> 该人员本月实际出勤为 0 天，请确认是否仍加入工资造资。

这样可以兼容特殊补助、补发工资等情况。

## 7.4 名单排序

工资名单默认排序建议：

1. 读取上一个工资月份该人员的工资排序；
2. 新出现人员追加到名单末尾；
3. 如果不存在上一月工资，则按当前考勤组 / 人员名单顺序生成。

生成后允许：

**长按拖拽调整人员顺序。**

顺序保存到当前工资批次。

例如：

```text
1 张三
2 李四
3 王五
4 赵六
```

10 月手工调整：

```text
1 王五
2 张三
3 李四
4 赵六
```

系统保存 10 月排序。

11 月生成工资时，默认优先继承 10 月人员相对顺序。

新人员自动追加到末尾。

# 8. 工资计算规则

每个人的工资明细至少包括：

- 姓名；
- 人员编号；
- 工种；
- 日薪；
- 实际出勤天数；
- 基础工资；
- 补助；
- 保险费用扣除；
- 最终工资；
- 备注。

计算：

```text
基础工资
= 实际出勤天数 × 日薪

最终工资
= 基础工资 + 补助 - 保险费用扣除

如果“基础工资 + 补助 - 保险费用扣除”小于 0，最终工资按 0.00 元计，并在异常检查中保留“保险扣除超过可发金额”的警告。
```

例如：

```text
张三
工种：绿化工
日薪：130 元
出勤：24.5 天
补助：300 元
保险扣除：150 元

基础工资：
24.5 × 130 = 3185 元

最终工资：
3185 + 300 - 150
= 3335 元
```

所有计算统一由业务层完成。

禁止直接在 UI Widget 中散落公式。

# 9. 出勤数据联动

工资模块不得重新维护一套出勤数据。

唯一考勤来源：

**现有月度考勤汇总。**

工资明细中的：

```text
实际出勤天数
```

默认只读。

点击出勤天数时：

进入该员工对应月份的：

**月考勤明细 / 月考勤表**

而不是直接在工资页面修改考勤。

如果发现工资出勤错误：

```text
工资页面
  ↓
跳转考勤
  ↓
修改原始考勤
  ↓
重新生成月度考勤汇总
  ↓
工资批次提示数据变化
```

# 10. 考勤变化后的工资联动

工资批次处于：

**草稿 / 待检查**

时，如果对应月份考勤被修改：

系统标记：

```text
考勤数据已变化
```

提供按钮：

**同步最新考勤**

同步时：

- 更新实际出勤天数；
- 更新基础工资；
- 重新计算最终工资；
- 保留用户已经填写的补助；
- 保留保险扣除；
- 保留人工日薪；
- 保留人员排序。

工资已经：

**已确认 / 已锁定**

后，考勤修改不得自动改变工资。

应显示：

> 该月工资已经确认，考勤数据发生变化。如需调整，请先解锁工资批次。

# 11. 日薪快照规则

工资生成时必须保存：

- 当时的工种名称；
- 当时使用的日薪；
- 日薪来源；
- 当时的实际出勤天数。

不能仅保存：

```text
jobTypeId
```

然后实时查询当前日薪。

否则以后修改工种日薪会导致历史工资发生变化。

例如：

9 月工资：

```text
绿化工
120 元/天
```

10 月将绿化工修改为：

```text
130 元/天
```

查看 9 月工资仍然必须显示：

```text
120 元/天
```

**每人每月一个补助金额 + 备注。**

字段：

- 补助金额；
- 补助说明。

例如：

```text
高温补助 300元
临时工作补助 200元
```

为了以后扩展，数据库建议不要只在工资明细保存一个 subsidyAmount。

推荐独立：

```text
payroll_adjustments
```

支持：

- 补助；
- 其他增加；
- 其他扣除。

但第一版 UI 可以只开放“补助”。

保险扣除属于工资当月的金额快照。

字段：

- 保险扣除金额；
- 保险扣除来源；
- 备注。

```text

```

- 是否参保；
- 参保单位；
- 保险类型；
- 办理状态；

直接：

**默认 0 元，并允许用户人工填写。**

# 16. 异常检查

确认工资前必须检查：

## 必须阻止确认

- 日薪为空；
- 日薪小于 0；
- 出勤天数小于 0；
- 工资结果计算失败；
- 同一工资批次重复人员；
- 人员记录已不存在且无法关联；
- 金额字段格式异常。

## 需要警告但允许继续

- 本月出勤为 0 但人工加入工资名单；
- 补助金额较高；
- 保险扣除大于基础工资 + 补助；
- 最终工资小于 0；
- 人员已离职但本月存在有效历史出勤；
- 工资工种与人员当前工种不一致；
- 考勤汇总尚未确认；
- 考勤数据在工资生成后发生变化。

异常必须显示：

```text
人员姓名
异常类型
问题说明
处理入口
```

# 17. 工资确认和锁定

## 草稿

允许全部修改。

## 待检查

异常检查完成，但仍可修改。

## 已确认

表示本月工资核算已经确认。

此时：

- 禁止自动同步考勤；
- 禁止修改日薪；
- 禁止修改补助；
- 禁止修改保险扣除；
- 禁止增删工资人员。

需要修改必须：

**撤销确认**

并记录原因。

## 已锁定

用于已经正式导出 / 报送后的工资。

解锁时必须：

- 输入解锁原因；
- 写入操作日志。

# 21. 核心计算函数

建议提供统一方法：

```dart
calculatePayrollItem({
  required int attendanceHalfDays,
  required int dailyWageCents,
  required int subsidyCents,
  required int insuranceDeductionCents,
})
```

由于考勤本身按照半天记录，业务层建议优先使用：

```text
attendanceHalfDays
```

例如：

```text
49 个半天 = 24.5 天
```

基础工资可以安全计算为：

```text
dailyWage × halfDays ÷ 2
```

避免 UI 层反复处理 0.5 小数。

金额按“元”使用 SQLite `REAL` 保存，业务层统一保留两位小数；出勤按整数半天保存。

# 25. 与离职功能联动

人员离职不代表当月没有工资。

例如：

```text
9月18日离职
9月1日—18日实际出勤 13.5 天
```

9 月工资仍然需要生成。

所以工资名单判断依据：

**工资月份的实际出勤**

而不是：

**当前是否在岗。**

离职后的后续月份没有出勤，则不进入默认工资名单。

如果整月出勤为 0：

默认不进入。

因此：

```text
人员状态

工资名单判断条件
```

# 52. 最终模块关系

```text
人员档案
   │
   ├── 用工类型
   ├── 工资工种
   └── 特殊日薪
          │
          ▼
月度考勤
   │
   └── 实际出勤天数
          │
          ▼
月度考勤汇总
          │
          ▼
临时工工资造资
   │
   ├── 工资人员名单
   ├── 人员排序
   ├── 日薪快照
   ├── 出勤快照
   ├── 补助
   ├── 保险扣除
   └── 最终工资
          │
          ├── 确认 / 锁定
          ├── 历史查询
          └── Excel 导出
```

核心原则：

> 考勤负责记录“干了多少天”，工资模块负责根据当月实际出勤和当时工资标准完成结算。

两者联动，但不重复保存和维护两套考勤逻辑。
