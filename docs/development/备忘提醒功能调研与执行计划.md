# 轻松办——备忘提醒功能调研与执行计划

> 文档日期：2026-09-16  
> 适用仓库：[yexufengjing/QingSongBan](https://github.com/yexufengjing/QingSongBan)  
> 当前阶段：阶段 0–6 已完成代码实现与自动化验收；Android 真机权限/Doze 验证需在发布前按设备矩阵执行。

## 1. 结论先行

轻松办已经具备一个可运行的本地提醒骨架，不应另起炉灶。现有项目已使用 Flutter、Riverpod、Drift、GoRouter、`flutter_local_notifications` 与 `timezone`，并已存在提醒表、Repository、列表页、表单页、通知服务、路由入口和基础测试。

本轮后续开发应采用“扩展现有 reminders 模块”的方式：

1. 保留现有技术栈和目录分层，不新增另一套状态管理、数据库或通知框架。
2. 把提醒分成“提醒主项、执行实例、通知规则、关联对象”四层，解决重复事项的完成历史、多人/多车关联和多次催办问题。
3. 继续复用 `flutter_local_notifications`，使用 `rrule` 计算复杂重复日期，使用 `flutter_timezone` 获取设备时区，不自行编写复杂日期递推和系统闹钟底层代码。
4. 首页增加“备忘提醒”业务入口；“我的”页保留为提醒设置入口。主页面采用今天/逾期/近期的任务式列表，不把所有操作继续堆在设置页。
5. 第一阶段先打通临时事项、工作计划、重复事项、人员关联、完成记录和本地通知。车辆、器械、物资关联预留统一接口，待对应业务表落地后直接接入。

## 2. 输入需求整理

### 2.1 用户文字需求

- 临时事项。
- 定期事项。
- 工作计划提前提醒。
- 重复提醒。
- 完成情况及完成时间。
- 关联车辆或人员。

### 2.2 图片需求归并

图片列出了以下业务提醒类型：

| 一级类别 | 具体场景 | 推荐产品处理方式 |
| --- | --- | --- |
| 通用事项 | 普通工作事项、重复工作事项、自定义事项 | 作为通用提醒类型，可选择一次性或重复规则 |
| 车辆 | 车辆保养、车辆年检、车辆保险 | 使用业务模板快速创建，并关联车辆 |
| 库存/物资 | 备件寿命到期、待采购物资 | 关联物资或采购记录；相关模块未落地前允许先记为普通事项 |
| 园林设备 | 园林器械保养 | 关联器械；相关模块未落地前保留扩展入口 |
| 财务往来 | 供应商待结款 | 关联供应商或采购单；相关模块未落地前保留扩展入口 |
| 人员 | 员工保险变更、每月福利领取 | 直接关联现有人员；可按月生成执行实例 |

图片要求的字段包括：标题、详细内容、重要程度、提醒时间、提前提醒天数、是否重复、重复周期、关联人员/车辆/器械/物资、完成状态、完成时间。重复周期需支持每天、每周、每月、每季度、每年和自定义。

### 2.3 需要补充明确的产品概念

为避免后期逻辑混乱，开发时必须区分以下概念：

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 事项重复 | 完成或到期后继续产生下一次事项 | 每月 5 日领取福利、每年车辆年检 |
| 提前提醒 | 在到期前的一次或多次通知 | 提前 7 天、提前 1 天、当天 09:00 |
| 未完成催办 | 到期后未完成时继续通知 | 到期后每天 09:00 提醒，最多 7 次 |
| 稍后提醒 | 用户临时推迟当前通知，但不改变原到期时间 | 1 小时后、明天上午 |
| 完成实例 | 某一次重复事项的完成记录 | 2026 年 9 月福利已于 9 月 6 日完成 |
| 提醒主项 | 一组重复事项共享的模板和规则 | “每月福利领取”这一长期规则 |

“重复事项”不能只用一条记录反复改日期，否则会丢失每月完成情况，也容易产生重复通知。正确方式是保留提醒主项，并为每个周期生成独立执行实例。

## 4. 开源项目与成熟方案调研

星级为 2026-09-16 调研时的 GitHub 数据，会随时间变化。

### 4.1 Super Productivity

- 项目：[super-productivity/super-productivity](https://github.com/super-productivity/super-productivity)
- 约 22,073 Stars，MIT License，本地优先的任务管理项目。
- 可借鉴优点：Inbox/Today 的任务视角、快速添加、计划时间与重复规则分离、标签/项目上下文、任务详情渐进展开。
- 对轻松办的启发：提醒首页应先展示“今天要做什么”，而不是先展示配置开关；快速创建只要求标题和时间，高级规则按需展开。
- 复用边界：技术栈不同，主要借鉴交互和领域拆分；不移植其 Angular/TypeScript 业务代码。

### 4.2 Tasks.org

- 项目：[tasks/tasks](https://github.com/tasks/tasks)
- 约 5,569 Stars，GPL-3.0 License，Android 任务与提醒项目。
- 可借鉴优点：相对提醒与绝对提醒并存、多提醒规则、稍后提醒、逾期提醒、筛选和重复任务处理。其历史更新也明确支持“提前分钟/小时/天/周”的相对提醒。
- 对轻松办的启发：提醒规则应存成独立集合；通知操作中应提供“完成”和“稍后提醒”；提醒状态应可用于筛选。
- 复用边界：GPL-3.0 具有传染性许可约束。除非未来项目整体接受 GPL，不能直接复制其代码；本项目只借鉴公开产品逻辑与交互思路。

### 4.3 Vikunja

- 项目：[go-vikunja/vikunja](https://github.com/go-vikunja/vikunja)
- 约 5,419 Stars，AGPL-3.0 License。
- 官方功能说明支持按时间间隔重复、周/月任务及多种任务视图：[Vikunja Features](https://vikunja.io/)。
- 可借鉴优点：一个任务包含到期时间、提醒、重复间隔、关联/负责人等独立属性；列表视图和状态视图可以相互切换。
- 对轻松办的启发：重复规则不应决定 UI 分类；“车辆保养”和“员工保险变更”仍是同一种任务实体，只是类别和关联对象不同。
- 复用边界：AGPL-3.0 代码不直接复制，只借鉴领域建模与页面组织。

### 4.4 flutter_local_notifications

- 项目：[MaikuB/flutter_local_notifications](https://github.com/MaikuB/flutter_local_notifications)
- 约 2,665 GitHub Stars；[pub.dev 页面](https://pub.dev/packages/flutter_local_notifications)约 7.35k likes，支持跨平台本地通知和按时区调度。
- 当前项目已经使用，应继续复用，不新增第二套通知插件。
- 应补齐的使用方式：`zonedSchedule`、通知点击回调、通知操作按钮、权限状态检查、待调度通知核对、创建/编辑/完成后的统一重排程。
- Android 13 及以上通知默认关闭，必须在用户主动启用提醒的上下文中申请权限；官方也建议先解释用途再请求：[Android 通知权限说明](https://developer.android.com/develop/ui/compose/notifications/notification-permission)。
- 轻松办默认继续使用不精确闹钟，降低权限和耗电影响。Android 官方说明，多数普通事项适合不精确闹钟；只有闹钟/日历等核心场景才应申请精确闹钟权限：[Android AlarmManager 指南](https://developer.android.com/develop/background-work/services/alarms)。

### 4.5 rrule

- 项目：[JonasWanke/rrule](https://github.com/JonasWanke/rrule)，Apache-2.0 License。
- 星级不高，但它是 Dart/Flutter 领域的专用成熟轮子；[pub.dev](https://pub.dev/packages/rrule)显示 150 pub points，并提供 RFC 5545 RRULE 的解析、生成和实例计算。
- 推荐直接依赖，用于每天、每周多选、每月、季度、每年、间隔周期和自定义规则，避免自行实现月底、闰年、跨年等日期算法。
- 注意：该包要求以 UTC 形式参与规则计算，并不负责设备时区；轻松办需要在领域层封装本地时间与 UTC/墙上时间的转换，并单独编写中文规则摘要。

### 4.6 flutter_timezone

- 包：[flutter_timezone](https://pub.dev/packages/flutter_timezone)，Apache-2.0 License。
- 用于取得设备当前时区，替换现有代码中写死的 `Asia/Shanghai`。
- 它是已停止维护的 `flutter_native_timezone` 的活跃替代分支，当前支持 Android、iOS、桌面和 Web。

### 4.7 调研后的“引用而非重造”清单

| 能力 | 采用方式 | 不采用的方式 |
| --- | --- | --- |
| 本地通知 | 继续使用 `flutter_local_notifications` | 自行编写 Android AlarmManager 插件 |
| 复杂重复日期 | 引入 `rrule` | 手写每天/月末/季度/闰年递推算法 |
| 设备时区 | 引入 `flutter_timezone` + 现有 `timezone` | 写死 `Asia/Shanghai` |
| 本地数据 | 扩展现有 Drift 表和迁移 | 新增另一套 SQLite ORM |
| 状态管理 | 延续 Riverpod Provider/StreamProvider | 混入 Bloc、GetX 等第二套框架 |
| 路由 | 延续 GoRouter | 页面内手工维护另一套导航栈 |
| UI | 复用现有 Material 3、主题色和通用组件 | 引入整套陌生 UI 框架 |
| GPL/AGPL 项目 | 只借鉴交互和领域思想 | 直接复制 Tasks.org/Vikunja 源码 |

依赖版本、许可证和“引用而非重造”边界已记录在[第三方依赖与许可证](第三方依赖与许可证.md)。

## 5. 推荐功能范围

### 5.1 第一阶段必须完成

1. 一次性临时事项与工作计划。
2. 每天、每周、每月、每季度、每年、自定义重复事项。
3. 标题、详细内容、优先级、到期时间、启用状态。
4. 一个事项可设置多条提前提醒，例如提前 7 天、1 天和当天。
5. 未完成催办：不开启、每天一次、每 N 小时一次；必须设置最大次数或截止时间。
6. 完成、取消完成、跳过本期、停用整个重复事项。
7. 每个执行实例记录状态与完成时间，长期事项保留历史。
8. 关联一个或多个人员；从现有在岗/暂停/离职人员中选择并显示状态。
9. 首页入口、今天/逾期/近期列表、筛选、搜索、快速新建。
10. 通知点击进入对应提醒详情；通知中提供“完成”和“稍后提醒”。
11. 通知权限、通知关闭状态和测试通知诊断。

### 5.2 第二阶段接入

1. 车辆、器械、物资、供应商等关联对象。
2. 车辆保养/年检/保险、备件寿命、器械保养、待采购、待结款等业务模板。
3. 从人员保险变更、每月福利等业务流程自动生成或更新提醒。
4. 关联对象详情页反向展示其提醒列表。
5. 提醒完成后跳转到对应业务办理页。

### 5.3 暂不纳入

- 云端推送、多设备同步和团队指派。
- 地理位置提醒、语音输入、AI 自动拆解计划。
- 完整日历/月视图拖拽排期。
- 短信、微信、邮件等外部通知。
- 未明确授权前不申请精确闹钟特殊权限。

## 6. 信息架构与 UI 方案

### 6.1 页面入口

| 位置 | 入口 | 用途 |
| --- | --- | --- |
| 首页 | “备忘提醒”业务卡片 | 高频入口；显示“今日、逾期”数量 |
| 首页 | 快速操作“新建提醒” | 直接打开精简新建页 |
| 我的 | “提醒设置” | 权限状态、默认提醒时间、默认提前量、测试通知 |
| 人员详情 | “相关提醒”区块 | 查看并新建关联此人的提醒 |
| 未来车辆详情 | “相关提醒”区块 | 查看车辆保养、年检、保险提醒 |

原“我的 > 本地提醒”建议拆分：待办列表迁往业务页，“我的”仅保留通知设置和诊断，避免高频任务与低频配置混在一起。

### 6.2 提醒首页

页面结构建议：

1. 顶部标题“备忘提醒”，右侧为搜索和筛选。
2. 三个统计筛选卡：今天、逾期、未来 7 天。
3. 分段选择：待办 / 计划 / 已完成。
4. 待办列表按“逾期、今天、明天、未来”分组。
5. 每张卡显示：完成按钮、标题、时间、优先级、重复摘要、关联对象 Chip。
6. 点击卡片进入详情；点击完成按钮后显示可撤销 Snackbar。
7. 右下角 `+ 新建`；首屏无数据时提供“新建第一个提醒”和模板入口。

不建议第一阶段做复杂日历，因为当前场景是现场管理人员快速查看和处理事项，议程列表的信息密度和操作速度更合适。

### 6.3 新建/编辑页

使用“基础信息 + 可展开高级设置”的渐进式表单：

**首屏必填区**

- 标题。
- 到期日期和时间。
- 快捷类型：临时事项、工作计划、定期事项、自定义。
- 提前提醒快捷选项：不提前、1 天、3 天、7 天、自定义。

**按需展开区**

- 详细内容。
- 优先级：普通、重要、紧急；状态不能只靠颜色，必须同时显示文字/图标。
- 重复：不重复、每天、每周、每月、每季度、每年、自定义。
- 结束条件：永不、截至日期、执行次数。
- 未完成催办及上限。
- 关联人员/车辆/器械/物资。
- 启用通知。

底部固定主按钮“保存提醒”。编辑页另提供“复制为新提醒、停用、删除”，删除与停用要明确区分。

### 6.4 快速模板

模板只预填字段，不建立独立业务代码：

- 车辆保养。
- 车辆年检。
- 车辆保险。
- 备件寿命到期。
- 园林器械保养。
- 待采购物资。
- 供应商待结款。
- 员工保险变更。
- 每月福利领取。

例如选择“每月福利领取”后，默认类别为人员事务、每月重复、默认上午 09:00，并引导选择人员；用户仍可修改全部字段。

## 7. 推荐数据模型

为降低迁移风险，保留现有 `reminders` 作为提醒主项，不进行大规模改名；数据库由版本 9 升级至版本 10。

### 7.1 reminders（提醒主项，扩展现表）

建议新增/调整字段：

- `details`：详细内容；可由现有 `remark` 平滑迁移或继续沿用 `remark`，二者择一，禁止重复语义。
- `priority`：normal / important / urgent。
- `category`：general / plan / vehicle / personnel / inventory / equipment / supplier / custom。
- `firstDueAt`：首个到期时间；现有 `dueDate` 可直接沿用以减少迁移。
- `timezoneId`：创建时区。
- `repeatRule`：RFC 5545 RRULE 字符串；一次性事项为空。
- `repeatMode`：fixedSchedule / afterCompletion，第一阶段默认 fixedSchedule。
- `repeatEndsAt`、`repeatCount`：重复结束条件。
- `isEnabled`、`archivedAt`、`createdAt`、`updatedAt`、`isDeleted`。

现有 `isCompleted` 不再作为重复事项的最终事实来源；一次性事项也通过执行实例记录完成，以统一逻辑。

### 7.2 reminder_occurrences（执行实例）

- `id`。
- `reminderId`。
- `scheduledAt`。
- `status`：pending / completed / skipped / cancelled。
- `completedAt`。
- `snoozedUntil`。
- `createdAt`、`updatedAt`。
- 唯一约束：`reminderId + scheduledAt`，防止重复生成。

该表解决“每月福利领取每个月各自是否完成”的追溯问题。

### 7.3 reminder_alert_rules（通知规则）

- `id`。
- `reminderId`。
- `offsetMinutes`：相对到期时间的分钟数；提前 1 天为 -1440，当天为 0。
- `isNagRule`：是否为逾期催办。
- `repeatIntervalMinutes`、`maxRepeatCount` 或 `nagEndsAfterMinutes`。
- `sortOrder`、`isEnabled`。

不再用单个 `leadDays` 承担所有提醒。迁移时把旧 `leadDays` 转成一条 `offsetMinutes` 规则。

### 7.4 reminder_links（关联对象）

- `id`。
- `reminderId`。
- `entityType`：employee / vehicle / equipment / material / supplier / purchase 等。
- `entityId`。
- `displayNameSnapshot`：保留创建时名称，防止关联对象删除后提醒无法理解。
- 唯一约束：`reminderId + entityType + entityId`。

当前阶段 `employee` 连接现有人员表。车辆等业务表尚不存在，不应伪造外键；先定义统一关联接口，待模块落地后再开放对应选择器。

### 7.5 scheduled_notifications（可选但推荐）

- `notificationId`、`occurrenceId`、`alertRuleId`、`scheduledAt`、`state`。

该表用于精确取消、重排程、查重和诊断。若第一阶段想控制工作量，可先在 Repository 中用确定性 ID 计算代替，待出现多端/复杂诊断需求再建表。

## 8. 核心实现方式

### 8.1 重复实例生成

1. UI 将用户选择转换为 RRULE，例如季度可转换为 `FREQ=MONTHLY;INTERVAL=3`。
2. `RecurrenceService` 使用 `rrule` 计算未来实例，不在 UI 或 Repository 中散落日期计算。
3. 采用滑动窗口：保证数据库内至少存在未来 90 天或未来 30 个执行实例，取较小数量上限。
4. 在创建、编辑、完成、跳过、应用启动/恢复时执行补齐；依靠唯一约束保证幂等。
5. 修改重复规则时，只重建未来未完成实例，已完成历史不得删除或改写。

### 8.2 通知调度

建立单一 `ReminderScheduler`，所有页面只调用 `reschedule(reminderId)` 或 `rescheduleAll()`，禁止页面自行调用通知插件。

调度流程：

1. 校验通知权限和提醒启用状态。
2. 获取设备时区并初始化 `timezone`。
3. 查询未来待办实例及其提醒规则。
4. 计算每个通知触发时间，过滤已过期的提前提醒。
5. 取消该提醒旧通知，再按确定性 notification ID 重新安排。
6. 将近期通知控制在安全窗口内，例如未来 30 天且总数不超过 50；应用恢复时滚动补齐。
7. 完成/跳过实例时只取消该实例通知，并生成或确认下一实例。

通知正文建议使用“到期时间 + 关联对象 + 详细内容摘要”，操作按钮为“完成”“稍后提醒”。点击正文进入提醒详情。

### 8.3 时区策略

- 使用 `flutter_timezone` 获取设备时区，禁止写死城市。
- RRULE 计算层遵循 `rrule` 的 UTC 输入约束，但把用户输入视为其选择时区下的“墙上时间”。
- 存储时保留 UTC 时间与 `timezoneId`；展示和调度时转换回指定时区。
- 设备时区变化后重新调度未来通知，并对“保持当地时间”与“保持绝对时刻”的规则统一采用前者，符合日常工作提醒习惯。

### 8.4 完成与重复的处理

- 一次性事项完成：当前实例标为 completed，记录 `completedAt`，取消未触发通知。
- 固定计划重复事项完成：仅完成本期，下一期保持原计划日期。
- 完成后重复事项：以实际完成时间为基准生成下一期；作为第二阶段高级选项。
- 跳过本期：状态为 skipped，仍保留下期。
- 停用整个事项：主项 `isEnabled=false`，取消所有未来通知，但保留历史。
- 删除：软删除主项，并取消未来通知；默认不物理删除历史。

### 8.5 业务联动

定义统一的 `ReminderLinkAdapter` 协议：

- 提供对象类型、对象 ID、显示名、图标和详情路由。
- 人员模块先实现 EmployeeAdapter。
- 车辆、器械、物资模块以后各自实现 Adapter，无需修改提醒核心表和调度服务。
- 业务记录变化时，使用稳定的 `sourceKey` 执行 upsert，避免每次保存都生成重复提醒。

## 10. 测试与验收清单

### 10.1 核心验收场景

1. 新建“明天 10:30 检查材料”，当天提醒，通知时间不能被改成 09:00。

6. 跳过本期后不再催办，本系列下期仍正常生成。

## 11. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 重复事项产生大量实例/通知 | 采用滚动窗口和数量上限，不一次生成多年数据 |
| 完成重复事项后历史丢失 | 主项与执行实例分表，完成只修改实例 |
| 重复通知 | 唯一约束 + 确定性 notification ID + 统一 Scheduler |
| 月末/闰年算法错误 | 使用 `rrule`，补充边界测试，不手写日期递推 |
| 时区错乱 | 设备时区 + timezoneId + UTC 存储策略 |
| Android 权限造成“保存了却没提醒” | 保存与通知权限分离，并持续显示诊断状态 |
| 精确通知增加权限和耗电 | 默认 inexact；只有明确需求后再评估精确闹钟 |
| 车辆等模块尚未存在 | 使用 Adapter 和通用 link 表预留，不创建虚假外键 |
| 开源许可风险 | 仅直接引入 Apache/BSD/MIT 等适配依赖；GPL/AGPL 只借鉴思想 |
| 页面复杂度过高 | 快速创建优先，高级设置渐进展开，模板负责预填而非新增流程 |

## 12. 开发硬性约束

1. 不重新实现本地通知、时区数据库、RRULE 解析等成熟能力。
2. 不引入与现有 Riverpod、Drift、GoRouter 职责重复的框架。
3. 任何通知安排必须经过统一 Scheduler，页面不得直接调插件。
4. 任何重复实例生成必须幂等，并由数据库唯一约束兜底。
5. 不直接复制 GPL/AGPL 项目代码。
6. 修改数据库必须提供升级迁移和迁移测试，不能只更新生成文件。
7. 已完成历史不可因编辑未来规则而丢失。
8. 状态不可只用颜色表达，重要操作必须有文字、图标和必要确认。
9. 车辆、器械、物资模块未落地前，只做接口预留，不制作不可用的假入口。
10. 本功能继续坚持本地优先，不强制云服务，不产生额外云成本。
