# 车辆年度油耗汇总表与附件中心开发执行方案

> 文件名称：油耗汇总.md  
> 适用项目：轻松办（QingSongBan）  
> 适用模块：车辆管理  
> 技术基线：Flutter + Riverpod + GoRouter + Drift/SQLite + file_picker + 现有备份恢复体系  
> 核心原则：单一数据源、只读汇总、软删除、附件本地化、避免重复统计与重复存储

---

# 一、总体方案

在现有车辆模块基础上补齐两个独立页面：

1. **年度油耗费用汇总表**：只读透视汇总，数据唯一来自 `fuel_monthly_records`。
2. **车辆附件资料**：复用人员附件中心的完整交互，包括上传、筛选、预览、导出、软删除和恢复。

月度油耗仍在单车详情页录入，汇总表不直接编辑单元格。点击单元格跳转至对应车辆的油耗页进行查看、修改或补录。

核心约束：

- 不新增年度汇总物理表。
- 不允许年度汇总表成为第二套数据源。
- 不重复保存维修附件和车辆附件。
- 所有汇总、统计、异常提示都从原始记录实时计算。

# 二、年度油耗横向汇总表

## 2.1 数据源与唯一性规则

年度汇总唯一数据源：

```text
fuel_monthly_records
```

业务上必须保证：

> 同一车辆、同一年、同一月份，逻辑上只能存在一条有效油耗记录。

建议在 Repository 层执行以下规则：

```text
查询 vehicleId + year + month
↓
不存在 → insert
存在且 isDeleted = false → update
存在且 isDeleted = true → 恢复并覆盖原记录
```

避免出现：

- 删除后重新录入导致同年月多条记录；
- 汇总时误重复累计；
- 软删除记录与新记录冲突。

如数据库条件允许，可增加唯一约束或唯一索引策略，但需要兼容软删除逻辑。

---

## 2.2 年度透视模型

新增年度透视模型和查询服务，不新增汇总数据库表。

查询规则：

- 按年份查询车辆和油耗记录；
- 固定生成 12 个月；
- 无数据月份显示 `—`；
- 每辆车占两列：
  - 油耗量/L
  - 金额/元
- 每月末尾显示：
  - 全车油量合计
  - 全车金额合计
- 底部显示：
  - 各车辆年度总油耗
  - 各车辆年度总油费
  - 各车辆有效月份平均油耗
  - 各车辆有效月份平均油费
  - 全车年度总计
  - 每月有效车辆平均值

车辆排序：

1. `vehicleNo`
2. 车辆名称

---

## 2.3 车辆是否进入某年度汇总的规则

不建议简单地把“所有未删除车辆”全部显示在所有年份中，否则多年后报废车辆会导致年度表越来越宽。

推荐进入某年度汇总的条件：

```text
当年度存在油耗记录
OR
当年度处于有效使用状态
```

如车辆档案后续增加：

- `commissionedDate`：启用日期
- `decommissionedDate`：停用/报废日期

则进一步采用：

```text
commissionedDate <= 当年12月31日
并且
(decommissionedDate 为空 OR decommissionedDate >= 当年1月1日)
```

这样可以保留历史统计完整性，又避免无关报废车辆持续占列。

# 三、统计口径

## 3.1 单车年度总计

```text
单车年度总油耗 = 当年所有有效月份油耗量之和
单车年度总油费 = 当年所有有效月份金额之和
```

空值按 0 参与总计。

---

## 3.2 单车有效月份平均

```text
单车平均油耗 = 单车年度总油耗 / 有效录入月份数
单车平均油费 = 单车年度总油费 / 有效录入月份数
```

注意：

- 不固定除以 12；
- 未录入月份不进入分母；
- 已软删除记录不进入分母。

页面建议明确显示名称：

- `有效月份平均油耗`
- `有效月份平均油费`

避免和自然月份平均混淆。

---

## 3.3 某月有效车辆平均

例如 3 月只有两辆车有记录：

```text
1#车 = 500L
2#车 = 600L
其他车辆 = —
```

则：

```text
3月有效车辆平均油耗 = (500 + 600) / 2 = 550L
```

不是除以全部车辆数。

公式：

```text
某月有效车辆平均油耗 = 当月有效车辆油耗合计 / 当月有效记录车辆数
某月有效车辆平均油费 = 当月有效车辆金额合计 / 当月有效记录车辆数
```

页面名称建议：

- `当月有效车辆平均`

---

## 3.4 全车年度总计

```text
全车年度总油耗 = 所有车辆当年有效油耗记录之和
全车年度总油费 = 所有车辆当年有效金额记录之和
```

# 四、数据完整度与漏填提示

原方案中的“已录入月份数”存在歧义，建议改为更清晰的指标体系。

页面可显示：

- 已录入月份：`6/12`
- 本月录入车辆：`5/6`
- 数据完整度：`91.7%`

数据完整度公式：

```text
实际有效记录数 / 理论应记录数 × 100%
```

理论应记录数只计算当年应参与统计的车辆和已进入的有效月份。

新增缺失记录提示：

> 2026年8月：2#洒水车尚未录入油耗。

该提示应与“油耗异常”分开，不混为一类。

# 五、异常提示优化

异常提示继续复用现有油耗异常服务，但建议分两层。

## 5.1 一级：统计异常

只根据数据变化提示：

- 本月油耗环比明显上升；
- 本月油费明显上升；
- 连续 3 个月增长；
- 明显高于近 3 个有效月份平均值。

推荐命名：

> 数据异常提示

而不是直接认定：

> 车辆油耗异常

---

## 5.2 二级：车况关联提示

如果同时存在：

```text
油耗上涨
+
发动机异常 / 油路异常 / 漏油 / 维修记录
```

则提示：

> 建议结合车辆当前车况检查。

不自动认定为机械故障。

# 八、单元格点击逻辑

汇总表只读，不直接编辑。

## 8.1 已有记录

点击任意：

- 油耗量单元格
- 金额单元格

都跳转到同一条记录：

```text
/vehicles/:vehicleId?tab=fuel&year=YYYY&month=M
```

进入编辑模式。

---

## 8.2 空记录

空单元格同样允许点击。

点击：

```text
某车 / 某月 / —
```

跳转到对应车辆油耗页，并自动带入：

- vehicleId
- year
- month

进入新增模式。

这样年度表可以同时承担：

> 检查缺项 → 快速补录

但仍保持“汇总表只读”的原则。

# 九、路由参数容错

单车油耗页解析：

```text
year 无效 → 当前年
month 无效 → 当前月
month < 1 或 > 12 → 忽略或纠正
vehicleId 不存在 → 错误提示页
```

如车辆已软删除，但历史记录仍存在：

> 允许以只读模式查看历史油耗记录。

避免历史统计断链。

# 十四、附件目录规则

附件目录：

```text
attachments/vehicles/{vehicleId}/
```

实际物理文件名不要直接使用原文件名。

推荐：

```text
UUID + 原扩展名
```

例如：

```text
attachments/vehicles/3/
8ab7f3e1-xxxx-xxxx.jpg
```

数据库保存：

```text
originalFileName = 维修照片.jpg
storedFileName = 8ab7f3e1-xxxx-xxxx.jpg
relativePath = attachments/vehicles/3/8ab7f3e1-xxxx-xxxx.jpg
```

防止同名文件覆盖。

# 二十、附件上传规则

继续使用现有：

```text
file_picker
```

单文件上限：

```text
20MB
```

必须执行：

```text
FilePicker 获取文件
↓
检查文件大小
↓
检查路径
↓
生成 UUID 文件名
↓
复制到内部附件目录
↓
计算 hash
↓
写入数据库
```

路径安全规则：

> 最终 real path 必须位于 App 私有 `attachments/vehicles/` 目录内。

拒绝：

```text
../../xxx
```

等路径穿越行为。

# 二十二、附件软删除与恢复

软删除：

```text
deletedAt != null
```

软删除后：

- 默认列表隐藏；
- 物理文件继续保留；
- 支持恢复。

后续可增加“附件回收站”。

永久删除才执行：

```text
删除数据库记录
+
删除物理文件
```

第一阶段不在软删除时删除物理文件。

# 二十三、维修附件统一原则

维修单不要另存一套照片路径。

统一使用：

```text
vehicle_attachments
```

例如：

```text
vehicleId = xxx
repairOrderId = xxx
category = repair
```

这样：

- 车辆附件中心可看到全部资料；
- 维修单只显示自己关联的资料；
- 不产生重复文件和重复记录。


```text

↓

↓

↓

↓

↓
```

建议增加：

```text

```

```json

  "schemaVersion": 13,

  "attachmentCount": 128

```

# 二十九、默认决策

1. 汇总表只读，不直接编辑单元格。
2. 空单元格允许点击并进入对应月份补录页面。
3. 不新增年度汇总数据库表。
4. 所有汇总均从 `fuel_monthly_records` 动态计算。
5. 单车平均按有效月份数计算。
6. 月度车辆平均按当月有效车辆数计算。
7. 车辆年度显示需考虑当年是否有效使用或存在历史记录。
8. 附件页面复用人员附件中心的完整能力。
9. 附件内部使用 UUID 物理文件名，保留原始展示名。
10. 软删除附件不删除物理文件。
11. 维修附件统一进入 `vehicle_attachments`，不重复存储。
12. 第一阶段先完成移动端横向汇总、Excel 导出、附件管理和备份恢复。
13. 打印、图片分享、内置 Office/PDF 高级预览暂不纳入本轮。

# 三十一、最终实施原则

这两个功能开发时必须坚持以下原则：

1. **原始数据只有一份。**
2. **汇总页面永远只计算，不存第二套汇总数据。**
3. **同车同年月只允许一条有效油耗记录。**
4. **平均值必须明确分母。**
5. **年度统计要考虑车辆实际有效年份。**
6. **附件数据库记录与物理文件必须一致。**
7. **软删除必须可恢复。**
8. **维修附件和车辆附件统一事实源。**
9. **备份时数据库与附件必须保证同一时点。**
10. **所有修改、删除、恢复后必须自动刷新相关 Provider。**

以上规则作为本功能开发、代码审查和最终验收的统一标准。
