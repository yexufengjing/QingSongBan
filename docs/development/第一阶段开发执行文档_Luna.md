> V2 是产品与业务规则基线；本文档用于明确 Luna 的开发顺序、阶段目标、文件组织、完成条件、禁止提前实现的内容和每阶段验收标准。

## 1. 总目标

完成“轻松办”第一阶段：人员管理与临时员工模块 Android 本地版。

技术栈固定：

- Flutter / Dart
- Riverpod
- GoRouter
- Drift + SQLite
- 本地通知
- Excel 导入导出
- 本地文件备份恢复

约束：

- 暂不接入服务器；
- 暂不接入云数据库；
- 不做登录系统；
- 不做多人协同；
- 不做工资计算；
- 优先 Android；
- 所有业务数据必须可离线使用。

## 2. Luna 执行原则

### 2.1 每次只完成一个明确任务块

禁止一次性生成整个项目。

每次任务完成后必须：

1. 保证项目可以编译；
2. 不留下明显报错；
3. 给出本次新增/修改文件；
4. 给出已完成内容；
5. 给出未完成内容；
6. 说明是否涉及数据库迁移；
7. 再进入下一任务。

### 2.2 不得擅自修改核心业务规则

以下规则固定：

- 基础考勤 = 上午 + 下午；
- 每个半天计 0.5；
- 加班独立按分钟保存；
- 人员状态与月度考勤名单分离；
- 请假、缺勤、公休、停工不能混为一类；
- 月度名单决定当月是否进入考勤；
- 历史数据不能因状态变化被覆盖。

### 2.3 优先可维护性，不追求一次写完

要求：

- 数据层、业务层、页面层分离；
- Provider 不直接堆 UI 逻辑；
- Drift DAO 不直接写复杂页面状态；
- 枚举统一定义；
- 日期、分钟、状态转换使用公共工具类；
- 不把魔法字符串散落在 UI。

## 10. 阶段 6：月考勤表

### 重点 UI

- 固定姓名列；
- 日期区域横向滚动；
- 支持 1～31 日；
- 行尾显示出勤、请假；
- 最后一行合计；
- 点击单元格编辑当天考勤。

### 符号

- 力：全天出勤；
- 半：开发阶段先使用标准临时符号；
- 后续替换为自绘“半力”；
- 🔺：缺勤；
- 休：公休；
- 停：停工。

### 汇总算法

每半天 = 0.5。

不要通过“实际小时 ÷ 8”计算第一版基础出勤。

### 验收

- 日考勤修改后月表同步；
- 月表修改后日考勤同步；
- 0.5 统计正确；
- 合计正确；
- 横向滚动不卡顿。

## 13. 阶段 9：离职

### 实现

- 人员状态 = 已离职；
- 离职日之后不可正常考勤；
- 后续月度名单默认排除；

### 验收

- 离职前历史不变；
- 离职后考勤被阻止；
- 撤销离职后不覆盖已有数据。

## 22. 开发控制原则

第一阶段最容易出问题的不是 UI，而是考勤数据模型。

因此必须坚持：

> 先稳定数据结构 → 再稳定每日考勤 → 再做月表 → 最后做汇总。

不要为了页面进度提前绕过数据库结构，也不要为了“看起来完成”使用临时假数据替代真实 Repository/DAO 流程。
