# 车辆管理模块开发执行文档

> 项目：轻松办（QingSongBan）  
> 模块：车辆管理  
> 适用车辆：环卫清扫车、洒水车  
> 技术基线：Flutter + Dart + Riverpod + GoRouter + Drift/SQLite + flutter_local_notifications  
> 架构原则：本地优先、尽量零额外费用、复用现有提醒/备份/Excel 导入导出能力  
> 文档用途：作为后续 Luna/Codex/人工开发的直接执行依据

---

## 1. 模块目标

车辆管理模块不是单纯的“车辆台账”，而应形成从 **车辆档案 → 当前车况 → 故障报修 → 维修处理 → 保养/备件寿命 → 油耗 → 单车费用分析 → 汇总预警** 的完整闭环。

本模块的核心目标：

1. 一眼看清每辆车当前是否正常、哪里存在问题、是否需要维修。
2. 每次维修、保养、更换备件都能形成永久历史记录，并自动影响车辆当前状态。
3. 轮胎、电瓶、液压泵、喷头、主机/副机保养等高频项目可计算使用天数、寿命与到期状态。
4. 维修费用、保养费用、备件费用、油耗费用能够自动汇总到单车费用分析。
5. 能看出某辆车“最近为什么费用高”“故障是否频繁”“油耗是否异常”。
6. 数据完全本地保存，接入现有备份恢复、Excel 导入导出、本地提醒体系。

# 3. 车辆档案

## 3.1 基本字段

车辆档案字段：

- id
- 车辆名称
- 车辆编号
- 车牌号
- 车辆类型
  - 环卫清扫车
  - 洒水车
- 品牌
- 型号
- 购置日期
- 使用部门
- 工作区域
- 责任人
- 当前车辆状态
  - 正常
  - 待维修
  - 维修中
  - 停用
  - 报废
- 备注
- 创建时间
- 更新时间
- 是否删除（软删除）

## 3.2 状态规则

车辆状态允许手工调整，但应有自动联动：

- 新建未处理报修单 → 自动建议状态“待维修”
- 维修单进入维修中 → 自动改为“维修中”
- 维修完成，且无其他未处理严重故障 → 自动建议恢复“正常”
- 停用、报废属于人工强状态，不被普通维修流程自动覆盖

为了避免程序错误修改状态，自动处理采用“建议 + 用户确认”或仅在明确流程节点自动执行。

# 4. 当前车况管理

当前车况不是简单备注，应按系统部件拆分，同时支持“快速总览 + 详细历史”。

## 4.1 总体状态等级

每个部件建议统一支持：

- 正常
- 轻微异常
- 需要关注
- 待维修
- 维修中
- 停用/不可用

部件异常不会直接等于整车不可用，但可以用于首页风险提示。

# 6. 轮胎管理 —— 重点业务设计

每辆车固定 6 个轮位：

1. 左前轮 LF
2. 右前轮 RF
3. 左后轮外侧 LRO
4. 左后轮内侧 LRI
5. 右后轮外侧 RRO
6. 右后轮内侧 RRI

## 6.1 重要原则：轮胎本体与安装位置分离

不能设计为：

`车辆表.leftFrontTireReplaceDate`

因为发生“倒胎”以后，轮胎实际身份发生位置变化，历史会错乱。

正确设计为三个概念：

### A. TireAsset —— 轮胎本体

每一条轮胎视为一件可追踪资产：

- tireId
- 轮胎内部编号（自动生成，例如 T-0001）
- 品牌
- 型号/规格
- 新旧属性
  - 新胎
  - 旧胎
  - 翻新胎（预留）
- 首次投入使用日期
- 当前状态
  - 使用中
  - 备用
  - 已拆下
  - 报废
- 累计修补次数
- 当前磨损等级
- 备注

### B. TireInstallation —— 安装履历

记录“某条轮胎，在什么时间，被装到哪个位置”。

字段：

- tireId
- vehicleId
- position
- installDate
- removeDate
- installReason
  - 新轮胎更换
  - 正常轮换
  - 倒胎
  - 修补后复装
  - 维修临时调整
  - 其他
- removeReason
- 来源位置（倒胎时使用）
- 操作备注

### C. TireRepair —— 修补记录

- tireId
- 日期
- 修补类型
  - 补胎
  - 火补
  - 冷补
  - 气门嘴
  - 其他
- 修补位置
- 修补程度
  - 轻微
  - 一般
  - 较重
- 费用
- 维修方
- 备注

## 6.2 倒胎操作流程

场景：某后轮损坏，需要更换；为了让新轮胎放在前轮，将原前轮移到后轮。

APP 内提供专门按钮：**“轮胎调位/倒胎”**。

操作示例：

1. 选择受损位置：左后轮外侧
2. 选择调位来源：左前轮
3. 选择新轮胎：新建轮胎或从备用轮胎选择
4. 系统显示预览：
   - 新轮胎 → 左前轮
   - 原左前轮轮胎 → 左后轮外侧
   - 原左后轮外侧轮胎 → 已拆下/报废/维修
5. 确认后系统一次事务完成三条履历变更

必须使用数据库事务，防止只换了一半导致位置数据错乱。

## 6.3 轮胎状态显示

六轮位用车辆示意布局展示，每个轮位显示：

- 轮胎编号
- 安装日期
- 当前连续使用天数
- 轮胎累计使用天数
- 磨损等级
- 修补次数
- 最近修补日期

磨损等级建议：

- 良好
- 轻度磨损
- 中度磨损
- 严重磨损
- 建议更换

支持自定义备注，如“花纹偏磨”“侧壁有裂纹”。

“连续使用天数” = 当前安装记录 installDate 至今天。

“累计使用天数” = 该轮胎所有安装履历的有效使用天数合计。

## 6.4 车辆模型化展示（轮胎/发动机/清扫装置可视化）

你的这个想法 **可以实现，而且非常适合车辆模块首页或单车详情“车况”页**。但第一版不建议做真 3D 建模，而建议采用 **“2.5D 伪立体车辆示意图 + 热区点击”** 的实现方式，成本低、交互清晰、后续也容易维护。

### 6.4.1 推荐实现形态

建议参考新能源车机里常见的“车辆总览”效果，但简化为：

- 视角：前侧上方 / 斜 45° 俯视
- 模型层次：
  - 驾驶舱
  - 车身/箱体
  - 发动机区域
  - 左前轮
  - 右前轮
  - 左后轮外侧
  - 左后轮内侧
  - 右后轮外侧
  - 右后轮内侧
  - 清扫装置
  - 喷头/水路区域
  - 灯光区域
- 每个区域支持点击
- 区域状态用颜色表达：
  - 绿色：正常
  - 黄色：需关注
  - 红色：待维修
  - 灰色：未配置/不适用

### 6.4.2 为什么不建议第一版直接做真 3D

真 3D 的问题：

- Flutter 端开发成本高
- 模型资源制作成本高
- 交互和性能调试时间长
- 后续你新增洒水车/扫路车不同车型时维护麻烦

而 2.5D 示意图的优点：

- 用一张 SVG/矢量图就能实现
- 每个部件都可以单独加点击热区
- 后续换样式、换车型比 3D 更轻
- 对你当前“轮胎、水路、发动机、清扫装置”场景已经足够好用

### 6.4.3 建议使用的参考结构

根据中联重科官方公开资料，中联重科环境产业覆盖扫路车、洗扫车等产品系列；其洗扫车官方介绍提到车辆通常由底盘、驾驶室、清扫装置、垃圾箱/水箱、副发动机、电控系统等部分构成，且清扫系统、喷杆/喷头等是关键作业部件。文档设计时可以把这些作为模型上需要突出展示的区域。

因此，扫路车示意模型建议至少保留：

- 驾驶舱
- 前桥/前轮
- 后桥双轮
- 发动机/副发动机区域
- 箱体（垃圾箱/水箱）
- 左右扫盘
- 吸嘴/清扫装置
- 水路喷头区域
- 灯光

洒水车示意模型则保留：

- 驾驶舱
- 发动机区域
- 前轮、后轮
- 水箱/大箱
- 前喷、后洒、侧喷
- 水泵/水路
- 灯光

### 6.4.4 UI 执行步骤

#### 第一阶段（推荐先做）

1. 为“扫路车”和“洒水车”各绘制 1 张简化示意图。
2. 示意图采用统一风格，不追求完全写实。
3. 在图上为各部件定义点击热区。
4. 点击轮胎 → 打开轮胎详情抽屉/弹窗。
5. 点击发动机 → 打开发动机状态卡片。
6. 点击清扫装置/水路/灯光 → 打开对应部件详情。
7. 部件有异常时，图上对应区域高亮提示。

#### 第二阶段（增强版）

1. 增加细一点的阴影和立体感。
2. 支持局部状态闪烁或角标。
3. 支持“问题筛选”，例如只高亮待维修部位。
4. 支持不同车型模板切换。

### 6.4.5 资源来源建议

可以参考中联重科扫路车/洗扫车公开图片做外观抽象，但不要把官方宣传图直接作为 APP 主界面成品使用。更适合的做法是：

- 用公开图片作为参考
- 抽象出轮廓、驾驶舱、箱体、扫盘、轮位布局
- 重新绘制成统一风格的简化 SVG

这样既能保留“像扫路车”的识别度，也能让界面更像业务系统，而不是宣传海报。

### 6.4.6 开发建议

Flutter 端建议：

- 第一版使用 `CustomPainter` 或 SVG 资源 + 命中区域
- 交互方式使用 `Stack + Positioned + GestureDetector` 或 SVG 命名节点点击
- 不新增重型 3D 引擎依赖

结论：

> 这个想法完全能实现，而且适合你的车辆模块。第一版最佳方案不是“高精度 3D 车模”，而是“中联重科扫路车/洒水车风格的简化 2.5D 车辆示意图 + 部件点击联动”。


### 6.4.7 本项目造型参考落地说明（结合用户提供的扫路车外观）

根据你补充的参考图，扫路车外观建议按以下特征抽象：

- 视角：**前侧上方斜视角**（接近车机系统里的车辆总览视角）
- 车头：白色驾驶舱，独立车头
- 车身：中后部为箱体结构
- 作业结构：车底两侧有扫盘/清扫刷
- 轮胎：前单轮、后双轮结构
- 色块：可以保留“驾驶舱浅色 + 箱体浅灰/功能区绿色点缀”的识别方式，但不追求完全复刻品牌配色

因此，第一版扫路车模型不需要做成高精度写实图，而应做成：

- 有明显驾驶舱
- 有明显箱体
- 有明显左右扫盘
- 有 6 个轮位的车辆示意图
- 有发动机、水路、灯光、清扫装置等点击区域

洒水车则沿用同一套风格，只把中后部功能件替换为：

- 水箱/罐体
- 前喷
- 后洒
- 侧喷
- 水泵/水路区域

这样能保证：

1. 用户一眼看出来是“扫路车 / 洒水车”；
2. 前端绘制难度可控；
3. 后续不同车辆共用同一套交互框架。

- 左前轮 LF
- 右前轮 RF

- 当前可见侧双后轮只能标注：
  - 右后轮外侧
  - 右后轮内侧
- 左后轮外侧、左后轮内侧属于隐藏侧，不在当前画面用悬浮标签跨车体指示；
- 旋转模型至车辆左侧视角后，再切换显示左后轮外侧、左后轮内侧。

交互层面仍必须保证全部 6 个轮位均可查看、点击，但**不是要求在同一视角同时出现 6 个标签**。

用途：

### 6.6.12 车辆模型左右方向、可见性与旋转交互最终规则（强制执行）

本节为根据原型复核后确定的最终规则，优先级高于前文中任何可能造成歧义的描述。

#### A. 左右方向判定标准

所有车辆部件的“左 / 右”必须统一采用 **驾驶员视角**：

> 驾驶员坐在驾驶室内，面向车辆正常前进方向时，其左手方向为车辆左侧，其右手方向为车辆右侧。

禁止根据：

- 手机屏幕的左边 / 右边；
- 用户当前观看图片时的视觉左右；
- 车辆图片在画布上的摆放方向；

来重新定义车辆左右。

数据库、枚举、UI 标签、维修记录、轮胎调位逻辑必须全部使用同一标准。

建议固定枚举：

```dart
enum TirePosition {
  leftFront,
  rightFront,
  leftRearOuter,
  leftRearInner,
  rightRearOuter,
  rightRearInner,
}
```

扫盘建议：

```dart
enum SweeperBrushPosition {
  left,
  right,
}
```

#### B. 当前模型默认视角

默认进入模型页时采用：

**车辆右前方斜上视角（front-right three-quarter view）**。

在该角度下应展示：

- 右前轮
- 右后轮外侧
- 右后轮内侧
- 右扫盘
- 中部吸盘装置
- 驾驶舱
- 发动机区域
- 灯光
- 箱体
- 水路区域

不应在该角度强行展示：

- 左前轮标签
- 左后轮外侧标签
- 左后轮内侧标签
- 左扫盘标签

这些隐藏侧部件在模型旋转到车辆左侧后再显示。

#### C. 扫盘结构规则

当前业务车型按以下简化结构实现：

- 左侧 1 个扫盘
- 右侧 1 个扫盘

即总计 2 个扫盘。

不得：

- 在一侧重复绘制两个扫盘热点；
- 将吸盘装置误认为第三个扫盘；
- 因透视角度而改变左右扫盘的业务身份。

#### D. 吸盘/吸嘴装置规则

吸盘装置属于独立清扫作业部件，应位于车辆底盘中部、左右扫盘后方或中间区域，模型中必须明确体现。

独立热点建议：

```text
partId: suctionAssembly
label: 吸盘装置
partType: suction
```

点击后至少显示：

- 当前状态
- 吸口/吸嘴情况
- 是否堵塞
- 是否变形/磨损
- 最近维修日期
- 最近更换日期（如适用）
- 是否需要维修
- 转报修入口

#### E. 旋转查看交互

模型必须支持旋转查看，不再把车辆模型定义为单张固定示意图。

第一版不要求实时 3D 引擎，可采用 **多视角 2.5D 图片/SVG 切换 + 拖动手势** 实现近似旋转效果。

建议至少准备 4 个视角：

1. 右前 45°（默认）
2. 右后 45°
3. 左后 45°
4. 左前 45°

如实现成本允许，可扩展为 6～8 个角度，以获得更平滑的旋转体验。

交互：

- 左右拖动模型区域切换视角；
- 显示左右旋转箭头；
- 显示“旋转查看”提示；
- 下方显示角度分页圆点或方向指示；
- 提供“重置视角”按钮，一键回到默认右前 45°；
- 切换视角后，热点标签同步切换，只出现该角度允许显示的部件。

#### F. 热点可见性配置

`VehicleHotspotConfig` 不能只有简单 `visible` 字段，建议增加视角控制。

推荐：

```dart
enum VehicleViewAngle {
  frontRight,
  rearRight,
  rearLeft,
  frontLeft,
}

class VehicleHotspotConfig {
  final String id;
  final String label;
  final VehiclePartType partType;
  final Rect rect;
  final Offset anchor;
  final Set<VehicleViewAngle> visibleAngles;
}
```

例如：

- `rightFrontTire`：`frontRight`, `rearRight`
- `leftFrontTire`：`frontLeft`, `rearLeft`
- `rightRearOuter`：`frontRight`, `rearRight`
- `leftRearOuter`：`frontLeft`, `rearLeft`
- `rightSweeperBrush`：右侧相关视角
- `leftSweeperBrush`：左侧相关视角
- `suctionAssembly`：根据模型遮挡情况，可在多个视角显示

具体热点坐标不能在不同角度共用同一个 `Rect`，建议按“车型 + 视角”建立独立坐标配置。

#### G. 数据层与视觉层必须分离

旋转只是视觉展示变化，不能改变部件真实身份。

例如：

- 数据库里的 `rightRearOuter` 永远代表右后轮外侧；
- 用户将模型旋转 180° 后，该轮胎即使出现在屏幕左边，也仍然叫“右后轮外侧”；
- 轮胎调位、维修记录、统计分析全部按业务身份处理，不按屏幕位置处理。

#### H. 原型页面视觉要求

模型页保留：

- 模型视图 / 列表视图切换
- 部件状态颜色说明
- 重置视角
- 旋转查看入口
- 当前问题列表
- 查看详情
- 转报修

默认右前视角的页面原型中，只需要重点标注：

- 右前轮
- 右后轮外侧
- 右后轮内侧
- 右扫盘
- 吸盘装置
- 发动机
- 灯光
- 驾驶舱
- 箱体
- 水路区域

隐藏侧通过旋转查看，不用为了“一张图显示全部部件”牺牲空间和方向准确性。

#### I. 本功能验收新增测试用例

必须增加：

1. 默认右前视角不出现左前轮、左后轮、左扫盘标签。
2. 默认右前视角正确出现右前轮、右后轮外侧、右后轮内侧。
3. 旋转到左前视角后，右侧隐藏部件标签消失，左侧对应部件出现。
4. 同一轮胎无论模型旋转到哪个角度，其 `TirePosition` 不发生变化。
5. 每侧只有一个扫盘热点。
6. 吸盘装置存在独立热点，能打开详情和转报修。
7. 左右拖动可以切换视角。

### 15.3.3 数据录入步骤（执行步骤）

建议采用 **“单车月度录入 + 年度汇总自动汇集”** 的方式，而不是直接编辑大表。

执行步骤如下：

1. 在单车详情页进入【油耗】页签。
2. 选择年份、月份。
3. 手工录入：
   - 油耗量（L）
   - 金额（元）
   - 备注（可选）
4. 点击保存。
5. 系统自动计算：
   - 平均油价 = 金额 / 油耗量
   - 该车年度累计油耗
   - 该车年度累计金额
   - 该车有效月份平均油耗
   - 该车有效月份平均油费
6. 保存后，该数据自动进入【年度油耗费用汇总表】对应月份行、对应车辆列。
7. 系统自动重算该月份整行的：
   - 月份油耗量总计
   - 月份金额总计
8. 系统自动重算底部“车辆总计”行：
   - 每辆车年度油耗总计
   - 每辆车年度油费总计
9. 系统自动重算底部“月份平均”行：
   - 每辆车油耗平均
   - 每辆车油费平均
10. 如修改或删除某月记录，汇总表同步刷新，不允许形成两套统计口径。

### 15.3.4 汇总计算规则（必须写死到开发规则中）

#### A. 单车年度总计

- 单车油耗总计 = 该车当年 1~12 月所有有效油耗量之和
- 单车金额总计 = 该车当年 1~12 月所有有效金额之和

#### B. 单车月份平均

- 油耗平均 = 单车油耗总计 / 有效录入月份数
- 金额平均 = 单车金额总计 / 有效录入月份数

注意：

- 分母是“有效录入月份数”，不是固定 12。
- 这样与当前人工表的管理习惯更一致。

#### C. 月份总计

- 某月油耗量总计 = 该月所有车辆油耗量合计
- 某月金额总计 = 该月所有车辆金额合计

#### D. 空值处理

- 未录入月份显示为空或“—”
- 计算总计时按 0 处理
- 计算平均时不计入有效月份数

### 15.3.5 交互与导出要求

- 支持导出 Excel，导出格式尽量贴近当前手工表版式
- 支持打印或图片分享（后续可选）
- 支持点击单元格查看该车辆该月份的原始油耗记录
- 支持从汇总表直接跳转到单车油耗记录页进行修改

### 15.3.6 开发实现建议

第一阶段推荐：

- 数据源仍然是 `fuel_monthly_records`

- 左列和表尾可做固定区，主体横向滚动

- 同一份数据出现两套真相

## 15.4 环比

`环比 = (本月 - 上月) / 上月 × 100%`

当上月为 0 或未填写时，不计算百分比，显示“—”。

## 15.5 异常油耗提示

基础版不做复杂 AI，采用透明规则。

推荐：

### 规则 A：相对本车近 3 个有效月份平均

当：

`本月油耗 > 近3月均值 × 1.25`

提示“油耗偏高”。

### 规则 B：金额异常但油量正常

油量变化 < 10%，油费上升 > 20%，提示：

> 油费增长较明显，可能与油价变化有关。

### 规则 C：连续增长

连续 3 个有效月环比为正，提示：

> 该车油耗已连续 3 个月上升，请结合工作量或车况核查。

异常只做提示，不自动认定车辆故障。

# 16. 单车费用分析 —— 核心设计

单车费用分析的定位不是简单“把维修费加起来”，而是回答：

1. 这辆车今年一共花了多少钱？
2. 钱主要花在哪里？
3. 哪个月费用突然升高？
4. 是油耗导致，还是维修导致？
5. 哪些部件反复维修？
6. 这辆车是否开始进入高维修成本阶段？

## 16.1 费用分类

建议统一费用分类：

### A. 油耗费用

自动来自油耗模块。

### B. 维修费用

自动来自已完成维修单“实际维修金额”。

### C. 保养费用

包括：

- 主机机油
- 副机机油
- 滤芯
- 常规保养工时

### D. 备件更换费用

例如：

- 轮胎
- 电瓶
- 液压泵
- 水泵
- 喷头
- 调整臂
- 灯具
- 清扫盘/刷

如果备件费用已经包含在维修单里，必须避免重复统计。

规则：

> 维修单内的备件金额统一归属于“维修费用”的子分类“备件”，费用分析可以拆分展示，但总成本只能计一次。

### E. 其他费用

允许人工录入：

- 年检
- 临时外协
- 清洗
- 喷漆防腐
- 其他

暂不强制设计保险、折旧，避免第一阶段过度复杂；后续可以扩展。

## 16.2 单车费用核心指标

单车费用页顶部显示：

- 本年累计总费用
- 本年油费
- 本年维修+保养费
- 本月费用
- 上月费用
- 本月环比
- 月均费用
- 单次维修平均费用
- 维修次数
- 本年最高费用月份

如果已有购置日期，可额外显示：

- 车龄（年/月）
- 本年非油耗维修成本

## 16.3 推荐统计口径

### 年累计总费用

`油费 + 维修费 + 保养费 + 独立备件费 + 其他费`

### 月平均费用

`本年累计费用 / 本年有费用记录的月份数`

也提供“自然月份平均”选项：

`本年累计费用 / 当前月份序号`

默认使用“当前月份序号”，更利于年度费用预算观察。

### 单次维修平均费用

`本年维修实际总金额 / 本年已完成维修次数`

### 非油耗维护成本

`维修 + 保养 + 备件 + 其他`

这个指标非常重要，因为车辆作业量越多，油耗自然增加，但维修成本异常更能反映车辆健康状况。

## 16.4 页面结构

### 区域 1：费用总览

卡片：

- 总费用
- 油耗占比
- 维修保养占比
- 环比

### 区域 2：月度费用趋势

横轴 1～12 月。

每月拆分：

- 油费
- 维修
- 保养
- 其他

可先采用“堆叠数据列表 + 总额”实现，图表后续增强。

### 区域 3：费用构成

展示：

- 油耗 xx%
- 维修 xx%
- 保养 xx%
- 备件 xx%
- 其他 xx%

### 区域 4：高频维修项目

自动统计维修记录中的“维修项目/系统分类”：

例如：

1. 水路：5次 / 1,260元
2. 电路：3次 / 820元
3. 制动：2次 / 690元

不做“好车/坏车”评分，只展示客观记录。

### 区域 5：异常费用提示

示例：

- 本月维修费用高于近 3 月平均 80%
- 液压系统 60 天内维修 3 次
- 本年度轮胎相关费用达到 3,200 元
- 本月油耗较上月增加 28%

## 16.5 单车费用分析与维修联动

维修单完成时：

- 实际金额自动进入车辆费用流水
- 明细类别自动进入维修子分类
- 更换轮胎、电瓶等可同步更新对应备件寿命

禁止用户再手工重复录入同一笔费用。

## 16.6 单车费用分析与油耗联动

油耗月记录保存后：

- 油费自动进入当月费用
- 修改油耗记录后，费用分析实时重新计算

不额外复制油费数据，避免双份数据不一致。

## 16.7 单车费用分析与保养联动

完成保养时填写：

- 材料费用
- 工时费用
- 总费用

自动计入对应月份。

## 16.8 后续可扩展指标

在有作业里程/作业小时后可增加：

- 每百公里油耗
- 每百公里成本
- 每作业小时油耗
- 每作业小时成本

对于环卫清扫车，**按作业小时成本通常比单纯百公里更有意义**；洒水车可同时保留公里和作业天数指标。

第一阶段不强制录入，避免增加日常工作量。

# 19. 关键唯一约束与数据规则

## 19.1 车辆

- 车辆编号建议唯一
- 非空车牌号唯一

## 19.2 油耗

同一车辆同一年同一月份仅允许一条：

`UNIQUE(vehicle_id, year, month)`

## 19.3 轮胎

同一车辆同一时刻，一个轮位只能存在一条未结束安装记录。

同一条轮胎同一时刻只能安装在一个车辆的一个位置。

调位必须在事务中完成。

## 19.4 金额

金额统一保存为 decimal-safe 方案。

在 Drift/SQLite 中建议存“分”为整数：

- 182.50 元 → 18250

UI 再格式化，避免浮点累计误差。

## 19.5 日期

- 业务日期使用本地日期
- 创建/更新时间统一存 DateTime
- 月份建议存 `YYYY-MM`

   ↓

# 31. 开发执行重点总结

本模块开发时最需要避免四个错误：

1. **轮胎只存位置，不存轮胎本体。** 这样一倒胎，历史必然混乱。
2. **费用在多个模块重复复制。** 应以原业务记录为事实源，费用分析统一聚合。
3. **保养状态靠人工填写。** 保养状态必须由上次日期 + 周期自动计算。
4. **车况只做一个长文本备注。** 应拆成部件和问题项，才能与维修联动、做统计和提醒。

第一版的核心价值不是做出很多页面，而是确保“记录一次，多处自动联动”：

- 一次维修 → 车况、备件寿命、维修历史、费用全部更新；
- 一次轮胎调位 → 六轮位和轮胎履历同时正确；
- 一次油耗录入 → 单车年度、全车汇总、环比、费用分析全部更新；
- 一次保养 → 保养状态、使用时间、费用和下一次提醒全部更新。

以此原则作为车辆模块所有后续开发与验收的统一标准。
