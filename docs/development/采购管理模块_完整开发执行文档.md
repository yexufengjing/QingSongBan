# 1. 模块定位

采购管理模块不是企业 ERP，也不替代公司 OA，不负责真正执行采购。

本模块只服务于用户本人日常采购申报跟踪工作，记录：

1. 小仓库物资库存不足或出现临时需求；
2. 在 App 中建立“待申报”采购记录；
3. 用户自行在企业 OA 中正式发起采购申请；
4. 在 App 中手动确认“已申报”；
5. 后续查询 OA 后，补充资材部采购分部、采购执行人、分配时间；
6. 手动进入“采购中”；
7. 从企业微信或 OA 收到物资入厂通知后，手动进入“待领取”；
8. 可调用 App 现有提醒功能设置领取提醒；
9. 用户完成企业 OA 领取流程并实际领取物资；
10. 在 App 中执行采购入库；
11. 库存模块自动增加库存并生成入库流水；
12. 完成后进入采购历史。

完整工作闭环：

```text
库存不足 / 临时需求
        ↓
创建采购记录
        ↓
待申报
        ↓
企业 OA 正式申报
        ↓
App 确认已申报
        ↓
已申报
        ↓
后续查询 OA，确认采购执行人
        ↓
采购中
        ↓
企业微信 / OA 收到物资入厂通知
        ↓
手动设为待领取
        ↓
可设置领取提醒
        ↓
实际领取物资
        ↓
App 执行采购入库
        ↓
库存增加 + 库存流水
        ↓
已入库
        ↓
采购历史
```

# 3. 技术基线

采购模块必须沿用“轻松办”现有技术体系，不新增第二套框架。

## 3.1 已确认技术栈

- Flutter + Dart
- Riverpod
- GoRouter
- Drift + SQLite
- flutter_local_notifications
- Material 3
- 本地优先、离线可用
- 暂不接服务器、云数据库、登录和多人协同

已有项目采用模块化 `features/*` 结构，数据库集中在 `core/database`，状态通过 Riverpod 管理。

## 3.2 分层原则

必须保持：

```text
UI Page / Widget
        ↓
Controller / Provider
        ↓
Repository
        ↓
DAO / Service
        ↓
Drift / 本地通知 / 其他本地能力
```

要求：

- UI 不直接调用 Drift DAO；
- Provider 不堆积大量 UI 拼装逻辑；
- DAO 不承担复杂页面状态；
- 状态枚举集中定义；
- 日期、数量、状态转换放公共工具类；
- 关键业务使用事务；
- 不在 UI 中散落魔法字符串。

# 5. 采购状态设计

## 5.1 状态枚举

```dart
enum PurchaseStatus {
  pendingApply,    // 待申报
  applied,         // 已申报
  purchasing,      // 采购中
  pendingReceive,  // 待领取
  stocked,         // 已入库
  cancelled,       // 已取消
}
```

数据库建议保存稳定字符串：

```text
pending_apply
applied
purchasing
pending_receive
stocked
cancelled
```

## 5.2 正常状态流转

```text
pending_apply
    ↓
applied
    ↓
purchasing
    ↓
pending_receive
    ↓
stocked
```

## 5.3 手工纠错

考虑 App 为个人自用工具，允许跳转状态，但必须二次确认。

允许例如：

```text
待申报 → 采购中
已申报 → 待领取
采购中 → 已入库
```

弹窗：

```text
当前操作将跳过部分采购状态，是否继续？
```

确认后：

- 更新主记录状态；
- 写入状态日志；
- 日志备注标记为“手动调整状态”。

# 6. 数据表结构

# 6.1 purchase_requests

采购主记录。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| id | TEXT/UUID | 是 | 主键 |
| title | TEXT | 是 | 采购事项名称 |
| status | TEXT | 是 | 当前状态 |
| request_date | DATETIME | 否 | App 创建日期 |
| applied_date | DATETIME | 否 | 企业 OA 实际申报日期 |
| oa_request_no | TEXT | 否 | OA 流程编号 |
| oa_title | TEXT | 否 | OA 流程标题 |
| oa_url | TEXT | 否 | OA 流程链接 |
| purchase_department | TEXT | 否 | 资材采购分部 |
| purchaser_name | TEXT | 否 | 采购执行人 |
| assigned_date | DATETIME | 否 | 分配日期 |
| arrival_notice_date | DATETIME | 否 | 收到物资入厂通知日期 |
| receive_location | TEXT | 否 | 领取地点 |
| demand_reason | TEXT | 否 | 需求原因 |
| remark | TEXT | 否 | 备注 |
| completed_at | DATETIME | 否 | 全部入库完成时间 |
| created_at | DATETIME | 是 | 创建时间 |
| updated_at | DATETIME | 是 | 修改时间 |
| is_deleted | INTEGER | 是 | 软删除 |

说明：

- `request_date` 与 `applied_date` 必须分开；
- “已申报”状态下 `purchaser_name` 允许为空；
- `arrival_notice_date` 只作为用户手动记录，不代表自动读取消息。

# 6.2 purchase_request_items

一张采购记录可以包含多个物资。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| id | TEXT/UUID | 是 | 主键 |
| request_id | TEXT | 是 | 主记录 ID |
| inventory_item_id | TEXT | 否 | 关联库存物资 |
| item_name | TEXT | 是 | 物资名称 |
| specification | TEXT | 否 | 规格型号 |
| unit | TEXT | 是 | 单位 |
| current_stock_snapshot | REAL | 否 | 建单时库存快照 |
| request_quantity | REAL | 是 | 申报数量 |
| received_quantity | REAL | 是 | 累计已入库 |
| remaining_quantity | REAL | 是 | 剩余待入库 |
| remark | TEXT | 否 | 明细备注 |
| created_at | DATETIME | 是 | 创建时间 |
| updated_at | DATETIME | 是 | 更新时间 |

逻辑：

```text
remaining_quantity
=
request_quantity - received_quantity
```

`received_quantity` 与 `remaining_quantity` 不允许 UI 任意直接编辑，应由入库业务更新。

# 7. 数据库事务要求

以下操作必须使用 Drift transaction：

```text
采购入库记录创建
+
库存流水创建
+
库存余额增加
+
采购明细 received_quantity 更新
+
采购明细 remaining_quantity 更新
+
采购主单状态判断
+
必要时 completed_at 更新
```

任何一步失败：

```text
全部回滚
```

禁止出现：

```text
采购显示已入库
但库存没有增加
```

或：

```text
库存已经增加
但采购记录仍显示未入库
```

# 38. 验收标准

采购模块上线前必须满足：

1. 可从库存物资快速创建采购；
2. 可手动创建新物资采购；
3. 5 个主状态正确流转；
4. 已申报阶段允许采购执行人为空；
5. 可补充采购分部、执行人、分配日期；
6. 可手动进入待领取；
7. 可联动提醒；
8. 支持分批入库；
9. 入库必须与库存事务一致；
10. 可查看完整采购时间线；
11. 可按记录查看采购历史；
12. 可按物资查看采购历史；
13. 可查看单物资采购周期；
14. 再次申报可自动带入物资基本信息；
15. 页面风格与已生成预览图一致；
16. 不出现价格、供应商、发票、付款等职责外内容；
17. 所有页面离线可正常使用；
18. 用户可进行必要人工纠错；
19. 不因状态编辑造成库存错乱；
20. 不新增与现有技术体系冲突的框架。

# 40. 最终开发原则

采购管理模块最终应始终保持：

```text
简单
稳定
清晰
可追溯
可手动修正
离线可用
库存一致
UI 统一
```

整个模块的核心不是“管理采购部门”，而是：

> **记录我申报了什么、现在进行到哪里、由谁采购、是否已经可以领取，以及最后是否进入我的小仓库。**

开发时任何新增功能如果偏离这一核心，应优先删除或简化，而不是继续扩展。
