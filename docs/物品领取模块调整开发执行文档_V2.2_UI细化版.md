# 物品领取模块调整开发执行文档 V2.2（UI细化版）

> 适用项目：QingSongBan（轻松办）  
> 模块：物品领取 / 福利劳保  
> 文档状态：开发前设计文档，当前阶段**仅用于确认方案，不直接修改功能代码**  
> 版本：V2.2  
> 继承：V2.1全部已确认业务规则，并进一步细化福利主页UI、点击区域、底部弹层、状态双向修改逻辑

---

## 1. 本版目标

本版重点不再讨论“有没有这些功能”，而是明确：

- 用户进入福利主页后第一眼看到什么；
- 每一个可以点击的位置在哪里；
- 点击后出现什么弹层/弹窗；
- 哪些操作不允许跳转新页面；
- 已领取与未领取如何直接通过姓名辨认；
- **已领取可以改回未领取，未领取也可以改成已领取，领取状态必须双向可修改；**
- 同一人员存在多个福利来源时，如何分别管理；
- 扫路车福利如何按车辆数量分配给正式司机；
- 公用福利如何指定给车辆组长；
- 页面如何尽可能接近现有纸质/Excel发放表的理解方式。

核心原则：

> **主页面就是发放表，名单就是状态表，姓名就是操作入口。**

---

## 2. 核心业务原则

1. 打开任意月份后，5秒内必须看懂本月应发情况。
2. 主页面优先展示：岗位、人数、人员名单、洗衣膏、手套、毛巾数量。
3. 不使用大量人员卡片作为主页主体。
4. 领取状态直接体现在姓名上。
5. 姓名本身可以点击，不需要额外放“领取”按钮占位置。
6. 已领取和未领取必须支持**双向切换**。
7. 扫路车、公用属于福利来源，不是虚拟领取人。
8. 所有福利最终必须绑定到真实人员。
9. 同一人可以同时有多个福利来源，来源之间状态独立。
10. 日常操作优先使用当前页、底部弹层、确认弹窗，尽量不跳第三层页面。
11. 手机竖屏采用“简化表格 + 名单”；横屏/平板采用接近现有Excel发放表的完整表格。
12. 福利劳保、办公用品、工具共用“物品领取”入口，但页面分开。

首页只保留一个入口：

> **物品领取**

点击后进入物品领取模块，顶部固定三个页签：

```text
[ 福利劳保 ]   [ 办公用品 ]   [ 工具 ]
```

默认进入：

> 福利劳保

本阶段开发只优先完成福利劳保。

首页不增加：

- 福利生成
- 未领取
- 扫路车福利
- 工具领取
- 办公用品领取

等多个快捷入口，避免首页变乱。

# 9. 人员名单显示规范

## 9.1 姓名状态

**未领取：**

- 默认深色文字；
- 不带✓；
- 保持醒目。

**已领取：**

- 绿色文字；
- 姓名后带 `✓`；
- 可以稍微降低字重，让未领取人员更容易被看到。

示例：

```text
张三✓   李四✓   王五   赵六✓   陈七   刘八   孙九
```

用户一眼看到普通深色姓名，就是尚未领取人员。

## 9.2 点击热区

虽然视觉上只是姓名，但点击热区不能只覆盖文字像素。

每个姓名建议使用最小约44px高度的可点击Chip/文字区域。

视觉上不必画明显边框，交互上必须容易点中。

## 9.3 状态不能只依赖颜色

已领取同时带：

> `✓`

从而兼顾：

- 屏幕颜色差异；
- 色弱情况；
- 打印截图时颜色不明显。

# 11. 已领取 → 改回未领取（V2.2新增强制要求）

## 11.1 为什么必须支持

实际操作可能出现：

- 误点领取；
- 别人代操作时记错；
- 当时以为已经发放，之后核对发现没有；
- 需要重新核对纸质签收记录。

因此状态必须允许：

```text
未领取 ⇄ 已领取
```

而不是单向：

```text
未领取 → 已领取
```

## 11.2 修改回未领取的交互

点击：

> 改为未领取

弹出轻量确认框：

```text
确认修改领取状态？

张三当前为“已领取”。
修改后将恢复为“未领取”。
原领取时间将保留在操作记录中。

[取消] [确认改为未领取]
```

确认后：

1. 当前有效状态改为未领取；
2. 姓名立即恢复默认深色；
3. `✓` 消失；
4. 汇总数字同步变化；
5. 原领取时间不作为当前状态显示；
6. **历史操作日志保留“曾于某时标记已领取、后改回未领取”的记录。**

目的：允许纠错，但不删除操作痕迹。

## 11.3 再次改为已领取

如果之后确认确实领取，重新点击姓名：

> 标记为已领取

生成新的领取时间。

历史日志示例：

```text
08-05 09:32  标记为已领取
08-05 10:08  改为未领取
08-06 14:20  再次标记为已领取
```

当前页面只显示最终状态，不展示完整日志；日志后续可从详情/操作记录查看。

# 12. 同一人员存在多个福利来源

例如张三既是正式工，又承担扫路车司机福利。

点击张三姓名后，不能只出现一个总状态。

底部弹层改为：

```text
张三
环卫车司机

本月福利来源

① 正式工标准福利
   洗衣膏1袋 / 手套1副 / 毛巾1条
   状态：已领取 ✓
   领取时间：08-05 09:32
   [改为未领取]

② 扫路车福利
   洗衣膏1袋
   状态：未领取
   [标记为已领取]
```

两个来源分别操作。

### 主页面姓名颜色如何判断

为了避免一个姓名既绿又黑无法表达，规则如下：

- 该区域只显示当前区域对应福利来源的状态。
- 正式工名单中的“张三”只代表正式工标准福利状态。
- 扫路车福利区中的“张三”只代表扫路车福利状态。

因此同一个人可以：

> 正式工名单里绿色✓  
> 扫路车福利区里仍是深色未领取

这是正确状态，不应合并。

# 21. 状态修改数据规则

每一条有效领取关系至少包含：

- 福利归属月份；
- 实际发放月份；
- employeeId；
- 人员姓名快照；
- 福利来源；
- 物品明细；
- 当前领取状态；
- 当前领取时间；
- 最后修改时间；
- 修改方式；
- 是否存在补领；
- 备注。

## 21.1 状态枚举

第一阶段只保留最清晰的：

- `notReceived` 未领取
- `received` 已领取

“待领取”不单独作为第三种状态，避免页面概念过多。

新生成名单默认：

> 未领取

## 21.2 双向转换

必须支持：

```text
未领取 → 已领取
已领取 → 未领取
未领取 → 已领取 → 未领取 → 已领取
```

不限制转换次数。

但每次变化必须写操作日志。

---

# 22. 操作日志要求

用户从已领取改回未领取时，不删除历史痕迹。

例如：

```text
2026-08-05 09:32 张三 正式工福利 标记已领取
2026-08-05 10:08 张三 正式工福利 改为未领取
2026-08-06 14:20 张三 正式工福利 标记已领取
```

主页只使用最后状态。

操作日志用于：

- 防止误操作无法追溯；
- 以后核对纸质记录；
- 判断是谁在什么时候改过状态（多人协同时）。

# 23. 重复领取与补领

重复领取判断必须使用：

> **月份 + 人员 + 福利来源 + 物品**

不能只判断：

> 月份 + 人员 + 物品

例如张三本月：

- 正式工福利：洗衣膏1袋；
- 扫路车福利：洗衣膏1袋；

这不是重复。

## 23.1 补领入口

只有已经领取的福利来源中显示：

> 补领

点击：

```text
补领

人员：张三
福利来源：正式工标准福利

物品：洗衣膏
数量：1袋
原因：
○ 破损
○ 遗失
○ 补发
○ 其他

备注：________

[取消] [确认补领]
```

补领是独立记录，不改变首次领取记录。

# 24. 临时工名单来源规则

临时工福利名单优先取：

> 福利归属月份对应的月度考勤名单

例如：

> 2026年8月发放7月福利

则读取：

> 2026年7月月度考勤名单

已离职人员如果7月份有实际考勤，仍可出现在候选名单中。

最终发放名单以用户手动确认结果为准。

# 25. 正式工福利岗位规则

正式工福利发放表建议使用“福利岗位”进行分组。

福利岗位可包括：

- 环卫车司机
- 绿化环卫组长
- 绿化技术员
- 车辆组长
- 其他

人员档案原岗位不强制等于福利岗位。

默认：

> 福利岗位 = 当前岗位

有特殊情况时再单独修改。

# 26. 福利规则

## 26.1 正式职工

每月：

- 洗衣膏1袋/人
- 手套1副/人

1月、7月：

- 毛巾1条/人

## 26.2 临时职工

每月：

- 洗衣膏1袋/人

单数月：

- 手套1副/人

1月、7月：

- 毛巾1条/人

## 26.3 扫路车福利

每辆每月：

- 洗衣膏1袋

不发：

- 手套
- 毛巾

车辆数量默认6辆，可修改。

## 26.4 公用福利

默认1份：

- 洗衣膏1袋

不发：

- 手套
- 毛巾

当前实际领取人默认推荐车辆组长。

# 28. UI视觉建议

## 28.1 状态颜色

已领取：使用项目主绿色体系。

未领取：使用默认正文深色。

不要使用红色表示未领取，因为“未领取”不是异常或错误。

只有真正的业务警告才使用橙/红色，例如：

- 扫路车6份却分配7人；
- 已领取人员被从名单删除；
- 重复补领。

## 28.2 表格风格

保持接近纸质表格的清晰边界：

- 表头底色轻；
- 数字居中；
- 岗位左对齐；
- 合计行加粗；
- 不使用过多阴影；
- 不将每一行都做成独立圆角卡片。

目的是“像一张现代化发放表”，而不是“像电商卡片列表”。

# 36. 最终验收标准

进入任意月份后，应在5秒内看懂：

1. 正式工有多少人；
2. 各福利岗位分别多少人；
3. 每个岗位具体有哪些人；
4. 临时工本月有哪些人；
5. 洗衣膏、手套、毛巾分别多少；
6. 扫路车有几辆、几份福利、分给哪几名司机；
7. 公用福利由哪名车辆组长领取；
8. 哪些姓名已经领取；
9. 哪些姓名还未领取；
10. 点击任意姓名可以直接修改状态；
11. **已领取可以改回未领取；**
12. 修改状态后页面立即刷新；
13. 不需要进入人员详情页面完成福利发放。

领取状态验收必须做到：

> **名单本身就是领取状态展示。**

状态修改验收必须做到：

> **未领取 ⇄ 已领取是双向的，且每次变更都有记录。**

扫路车与公用验收必须做到：

> **它们只是福利来源，最终每一份都绑定实际人员。**

# 37. 本版最终结论

V2.2在V2.1基础上重点确定以下交互：

1. 福利主页采用“汇总表 + 人员名单”，不再使用大量人员卡片。
2. 人员姓名既承担状态显示，也承担状态修改入口。
3. 已领取姓名使用绿色 + ✓；未领取使用普通深色。
4. 点击未领取姓名，可以立即改为已领取。
5. **点击已领取姓名，可以明确改回未领取，并保留操作日志。**
6. 同一个人的正式工福利、扫路车福利等不同来源分别管理，不合并状态。
7. 扫路车数量决定福利份数，福利分配给正式员工司机。
8. 公用福利实际绑定车辆组长。
9. 绝大部分操作使用底部弹层完成，不增加过深跳转。
10. 本文档确认后，才进入下一步代码重构。
