# 车辆费用分析 Agent 行为与验收草案 v0.1

日期：2026-10-18。状态：用户已确认本草案，授权制定执行方案并开始改造；不代表这些能力已经实现。现有增量版的自动验证记录保留，体验验收仍为未通过。实施依据见《车辆费用分析Agent开发执行方案_v1.0.md》。

## 1. 已确认的目标

用户希望同时提升模糊需求理解和自主多步执行，首个完整场景为：

> 在车辆页面说“这辆车最近怎么这么费钱”，助手自行查费用、对比历史、找主要费用来源，给出有依据的解释。

- 泛指“费钱”时分析全部已登记费用；明确提维修、油费、保养等时聚焦对应类别。
- 未明确时间且对话、页面没有适用条件时，默认最近30天，对比前30天。
- 数据少时可查看近90天补充背景，注明实际范围；不悄悄替换原30天问题。
- 可以主动查看同类车辆作参照，结合可用里程或工作量判断；不可比时只作参考，不直接认定异常。
- 继续个人自用、DeepSeek BYOK、业务只读。原有考勤、年度维修汇总、排名和来源入口保留。

## 2. 期望的一次完整体验

| 环节 | 助手应有的行为 |
|---|---|
| 理解 | 识别“费钱”“最近”“这辆车”等表达，不要求用户使用固定句式或逐项填条件 |
| 对象 | 使用当前明确选择及有效会话上下文；点击新车辆页“问助手”视为重新选车；确实无法唯一确定时才提供一次候选选择 |
| 时间与范围 | 自动采用已确认规则，在结果中简短注明对象、日期及费用类别；支持直接说“只看维修”“换上个月”等修正 |
| 自主查询 | 根据已有结果选择下一步：对比前期、细分增长来源、补查历史或参考同类车；证据足够即可停止，不机械跑满所有步骤 |
| 分析 | 区分费用总额变化、类别贡献、发生次数、集中度和可用工作量；数值由本地业务工具计算 |
| 结论 | 先回答主要变化来自哪里，再列少量关键依据及必要的待核实点；不能把用户“费钱”的感受直接当作异常事实 |
| 继续使用 | 已确认的车辆和条件可沿用；用户能短句追问、纠正、停止，也能一键查看原页面 |

查询不预设一个需要逐步确认的向导。界面只展示简短进度，例如“正在对比前后费用”，不展示模型内部推理或要求用户批准每次只读查询。

## 3. 按现有数据粒度分析

已核对现有代码：油费记录为月度数据，包含金额、油量及可选工作天数、里程、工时；维修、保养和手工费用有业务日期。

- 日级费用：最近30个自然日包含今天；比较此前连续30日。具体边界在本地计算，不让模型自行算日期。
- 油费：单独按月分析，标明月份和登记覆盖。不得按某月第一天归属整月费用，也不得平均摊成每天后伪报精确的近30天金额。
- 不同粒度分别呈现；仅在时间口径一致时给出合计和增幅。本月未完整、缺记录、上一期为零等情况分别处理，不将缺失当作零支出。
- 维修延续既有统计口径：已完成、未删除维修单，采用实际金额并按报修日期归属。保养用执行日期，手工费用用费用日期；不改原页面保存与统计规则。
- 跨车比较至少核对车型、同一期间、费用类别及登记覆盖；使用单位里程或单位工作量指标时，分子与分母期间必须一致。
- 仅有金额差异或缺少可比工作量时，可以说明参考差异，不能据此认定车辆、驾驶或使用行为异常。

## 4. 所需的改造方向

当前实现主要是一次意图解析后进入预设查询分支，车辆接口以年度汇总、排名为主。新增场景需要实际的多轮工具执行能力，不能仅修改提示词或增加口令。

建议保持现有业务层，新增一个小型会话执行器：

1. 把车辆上下文和允许的只读工具交给模型，模型选择查询目标与工具参数。
2. App 校验参数，本地执行并返回必要的匿名汇总、覆盖情况和可比性结果。
3. 模型据返回结果决定继续查什么或结束；失败时保留已取得的事实，不把失败伪装为空数据。
4. 回答中的金额、日期、对比数值必须能回指本地结果，来源导航继续由 App 构造。

业务工具按职责提供：期间费用汇总、前后期比较、费用增长来源、同类车辆参照及必要的数据覆盖查询。工具的最终名称、字段、预算和错误约定在执行方案中固定；不开放任意 SQL、路由或数据库方法，不引入无关框架或业务写入。

旧版“车辆通常只调用一次模型”不作为本轮限制；多轮调用必须有停止、总预算和提前结束条件。继续复用当前模型与设置，不增加第二模型、语音、系统悬浮窗或无关页面改版。

## 5. 数据发送与结论依据

- 沿用必要汇总外发原则：允许后续接口设计列出日期范围、费用分类金额/次数、匿名比较汇总、工作量及覆盖标记等必要字段。
- 数据库姓名、车牌、内部 ID、逐条单据、自由文本症状和备注不自动发送；明细外发仍需单次确认具体字段和范围。
- 第一版先用结构化费用和工作量说明变化来源。若需要未获允许的明细才能继续，应保留已确认的分析并明确缺少的依据，不编造故障原因。

## 6. 验收标准

| 情形 | 必须出现的表现 |
|---|---|
| 车辆页“最近怎么这么费钱” | 无需先填日期和类别，即可开始分析并展示采用的条件 |
| “只看维修”“换上个月”“和同类车比呢” | 识别为范围修正或深入分析，沿用仍适用的对象与条件 |
| 主要增长集中于某一类别 | 自主追查有意义的来源，回答包含本地计算的贡献依据，而非只复述总额 |
| 同类车工作量差异明显 | 能结合可比数据调整判断；不能只凭总金额排高就说异常 |
| 油费仅有月度记录 | 清楚采用月度比较，不伪造日级或同期精确值 |
| 数据不足、无法比较、没有明显增长 | 如实给出当前能确认的结果，可自动补查背景；不为了附和问题编造“费钱”的原因 |
| 车辆歧义或对象纠正 | 必要时一次选择；换车后正确分析新车，在途请求不被新页面偷偷改对象 |
| 断网、超时或主动停止 | 可停止、保留已取得的事实与问题，不自动反复调用或要求重填全部条件 |

验收以模糊表达理解、工具选择、自主追查、结论依据及实际输入/选择次数为主，不以固定口令通过数代替。正金额、费用结构变化、不同工作量及缺数据场景使用隔离测试库；不向现有模拟器业务库补造记录，不读取导出已保存 Key。

本人最终试用应直接判断：是否可以用自己的话提出问题，是否减少输入与确认，是否能得到有帮助且可核对的分析。现有增量版的验收结论不自动转为本轮通过。
